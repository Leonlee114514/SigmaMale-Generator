> 📖 这是**详细文档**：设计细节、踩坑记录、实测数据、验证口径都在这里。
> 项目简介与快速上手请看 **[../README.md](../README.md)**。

对着摄像头做动作，实时合成 sigma / gigachad 风格画面；录完的素材配上一首固定
BGM（gigachad theme / phonk house），按 BGM 的**节拍分析**做卡点变速，
导出可直接发平台的竖屏短视频。

项目位置：`C:\Users\Lyonl\Desktop\SigmaMaleGenerator\`

> **三条成片路线**
> - `edit_ref.py` —— **参考片完全复刻器**：照搬 `2022年的剪辑 belike.mp4` 的
>   结构（67.12BPM / 15 镜 × 1 拍 / 黑白镜序列），只把实拍位换成自己的素材。
> - `edit_slop.py` —— **卡点剪辑器**：实拍 + 交错素材交替快剪，含闪白/抖动/色差/颗粒。
>   按 128BPM 拍网格自动切。
> - `bgm_pipeline.py` —— 单素材卡点：把一段素材变速到正好 N 个强拍，配 BGM。

### ★ 一条命令跑完（推荐）：slop_pipeline.py

```bash
"$PY" slop_pipeline.py --template both \
    --footage output/新素材_原始.mp4 \
    --material "C:/Users/Lyonl/Desktop/2022年的剪辑 belike.mp4" \
    --face-crop --grade
```

它把原本要手动依次跑的 6 个脚本串起来，并且把**验收做成门禁**：

```
前置自检 → 动作检测 → 切片+映射 →（调色）→（人脸特写）→ 成片 → 验收
                                                              ↑ 不过就非零退出
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--template ref/slop/both` | 出哪条模板（ref=照搬参考片结构；slop=128BPM 卡点） |
| `--clips 映射表.json` | 复用已有动作分析，跳过检测与切片 |
| `--skip-detect` | 复用 `output/_pipeline/` 里已有的检测结果 |
| `--face-crop [ZOOM]` | 人脸特写（默认 3.0x），`--face-lock` 加锁头运镜 |
| `--grade` | 先调色再出片（会自动把映射表重指向调色版，并校验时长一致） |
| `--dry-run` | 只打印将执行的命令 |
| `--no-verify-gate` | 验收不过也返回 0（**只用于排查**） |

**为什么卡点版要多渲一版"验收专用片"**：`edit_slop` 每一镜都带逐镜变换
（镜像/分屏/缩放/负片/倒放），像素对应关系被破坏 —— 在正式成片上做内容匹配
是无意义的（实测只有 3/11 胜出，而那不是选段错）。所以编排器会额外渲一版
`--no-fx` 且关掉全局特效的诊断片专门用于内容验收；
节奏类验收（闪白/硬切）仍在正式成片上做。

> ⚠⚠ **验收专用片必须与成片"是同一份方案"，否则验收是在验另一部片子。**
> 2026-09-25 实测踩到两个坑，都表现为"内容匹配未胜出"（看着像选段错了）：
>
> **坑 1：`--no-fx` 会破坏「微波炉对」的识别。**
> `--no-fx` 把所有 `rev` 置为 `False`；而配对识别当时依赖 `rev`，
> 于是微波炉的两半被分到不同入点（镜 22/23 变成 **1.039 / 10.758**），
> 方案整体走偏。→ 已改成**只按"入点完全相同"识别**（非配对镜的入点每镜
> 推进 0.633s，只有一对的两半才相同，是充分指纹）。
>
> **坑 2：验收片不带 `--face-crop`，成片带。** 两个源不是同一个文件，
> 只要时长差一帧，`pick_intro_offset` 就可能选出完全不同的方案。
> → 保留这个差异（带上要重跑一次人脸特写，慢 2 分钟），但在
> `slop_pipeline.step_render_diagnostic` 里**硬性比对两边的逐镜入点**，
> 不一致就当场 `Fail`，不放进验收。
>
> 这两个坑都属于同一类：**"验收的对象"和"交付的对象"悄悄不是同一个**。
> 项目里已经因为同类问题栽过两次（特征缓存不绑定源文件、文档里的数值不绑定
> 素材），这是第三次 —— 所以这次直接做成了机器检查，而不是靠人记得。
>
> **顺带修的第三件：判据本身太苛刻会"每次都报红"。**
> `verify_contentaware` 原来只认两种结论：严格胜出，或"高分 + 差距 <0.05"的
> 近平局。实测卡点版镜 31（"嘟嘴"）锚点 **0.906**、对照 0.976 —— 差 0.070，
> 刚过阈值就被判"未胜出"。但把三帧（成片 / 入点 / 入点−1.2s）抽出来逐张看，
> **姿势几乎完全一样**（用户只是坐着看镜头），差别是亚像素头位 + 压缩噪声。
> 而脚本自己的注释早就写了：真·选段错会让锚点**塌到 0.1~0.5**。
> → 补一条规则：**锚点已达 0.85+ 时，只要不是被大幅（>0.15）超过，一律记
> "近平局"**。理由很实际 —— 一个每次跑都报红的验收，很快就不会有人看了，
> 那比漏报更糟。

中间产物与每步日志落在 `output/_pipeline/`（含 `log_验收_*.txt`）。

## 成片自动命名（film_name.py）

**为什么要专门做**：原来 `out_name()` 只用「模板名 + 画幅」，
模式参数完全不进文件名 —— 于是**不同模式静默互相覆盖**。真实事故：
勾了「人脸特写+锁头」出片，输出的仍叫 `卡点_竖屏.mp4`，把普通版覆盖掉了，
事后只能翻同名 `.plan.json` 的 `source` 字段才知道是哪种源做的。

而且成片有**两个出片入口**，各有各的毛病：

| 入口 | 原来的名字 | 问题 |
|---|---|---|
| 网页流水线 | `卡点_竖屏.mp4` | 模式不进名 → 互相覆盖 |
| `卡点成片.bat` | `slop_edit_20260925_221530.mp4` | 不传 `--out`，走时间戳兜底名，看不出是什么 |

### 规则

```
<模板>_<画幅>[_模式词...]
```

token 用 `_` 连接、空值跳过，固定顺序 **构图 → 节奏 → 色彩 → 效果**：

| 模式词 | 触发 |
|---|---|
| `人脸特写` | `--face-crop` 给了值 |
| `锁头` | `--face-lock` |
| `安全区` | `--face-safe-y` |
| `极碎` | `--slices >= 2` |
| `调色` | 流水线 `--grade`（**预**调色） |
| `降饱和` | `--bw > 0` |
| `无特效` | `--no-fx` |

```
卡点_竖屏.mp4
卡点_竖屏_人脸特写.mp4
卡点_竖屏_人脸特写_锁头.mp4
卡点_竖屏_人脸特写_锁头_极碎_调色.mp4
复刻版_方形.mp4
```

**版本号**：首次裸名，其后 `_v2` / `_v3`…（**绝不覆盖**）。
取 **max+1** 而不是"最小空闲号"—— 只有单调递增，"号最大 = 最新"才成立；
本项目真发生过"把 `_v2` 挪走"，最小空闲号会立刻把那个号重新用掉。

**所有模式词不带数字**：版本号扫描用 `^<主名>(?:_v(\d+))?$`，
词里混数字的话 `降饱和35` 那个 35 是参数还是版本号，人和正则都难判断。
精确参数值一律记进 plan.json。

**不进名的**：`内容感知`（`--clips` 现在默认常开、没区分度）、
`peak-pos` / `intro-pick`（调优旋钮）、`grain` / `rgb` / `shake` / `flash`
（微调，几乎永远默认值）、`dry-run` / `skip-detect` / `progress`（不影响画面）。

### plan.json 的 `render` 段

除了文件名，渲染参数也**记进方案**，工具不必再解析文件名去猜模式：

```json
"render": {
  "template": "卡点", "aspect": "vertical",
  "face_crop": null, "face_lock": false, "face_safe_y": null,
  "slices": 1, "bw": 0.0, "no_fx": false,
  "clips": "output/_pipeline/reel_map_used.json",
  "out": "卡点_竖屏_v4.mp4"
}
```

> ⚠ **存量文件会占版本号** —— 这是"绝不覆盖"的技术保障，但第一次会有点意外：
> 改造时 `output/` 里已有 `卡点_竖屏.mp4` 与 `卡点_竖屏_v3.mp4`，
> 所以**第一次跑普通版得到的是 `卡点_竖屏_v4.mp4`**（不是覆盖，是续号）。
>
> ⚠ `调色` 词只由**流水线**添加（它的 `--grade` 是预调色）。
> `.bat` 路径没有预调色，本来就不该有这个词。
> 别和 `edit_slop --no-grade`（编辑器自己那道轻调色）搞混 —— 那是另一回事。

回归测试：`python test_film_name.py`（含版本扫描、存量避让、默认值不进名）。

## 交错素材怎么挑（很反直觉，先看这条）

**素材是从头「顺序消耗」的，不是随机取用。** 快剪段里每个素材镜推进
`0.633s`（0.469s × 1.35 变速），实拍/素材交替，所以一部片只用到素材的
**前约 7 秒**（22 刀里约 11 个素材镜 × 0.633s）。

后果很硬：

- 素材**后段再好也看不见**；前 7 秒是什么，成片里就是什么
- 想换观感，**要动的是前 7 秒**，不是整段重做

**踩过的实例**：原素材 `2022年的剪辑 belike.mp4` 是 30 秒，但**前 19 秒
全是同一个抽雪茄镜头**（后段才有别表情，最后 3 秒还是灰底片尾）。
成片里因此几乎只有"贝特曼抽烟"，看着很单调 —— 而素材本身并不缺内容，
只是**好东西放错了位置**。

**现在用的素材**：`output/交错素材_贝特曼表情.mp4`（10.2s / 360×360 / SAR 1:1），
全部是脸部特写，且**把最经典的表情排在最前面**：

| 位置 | 内容 |
|---|---|
| 0.0-2.2s | 侧头点头 + 抬手指（sigma 招牌姿势） |
| 2.2-3.3s | 皱眉 |
| 3.3-4.2s | 嘟嘴 |
| 4.2-5.1s | 皱眉 —— 经典 sigma face |
| 5.1-6.4s | 抿嘴笑 / smirk |
| 6.4-7.2s | 大笑 |
| 7.2s 之后 | 脸部特写（基本用不到，留着以防编排改多素材镜） |

### 做素材时踩到的三个坑

1. **必须 1:1（方形），且 SAR 要 1:1**。
   归一化链对 1:1 源是"铺满 1080x1080 居中"，对 9:16 源会**铺满整帧** ——
   那样素材镜就和实拍镜长得一样、失去区分度。
   ⚠ 而 `face_crop.py` 的输出是 **360x360 像素但 SAR 9:16（变形像素）**，
   直接用会被当成 9:16 处理。要先 `scale=360:640,setsar=1` 还原方形像素再裁。

2. **不能对原始源用固定 Y 裁方形**。源是多镜头拼接，脸的高度每个镜头都不同，
   固定裁会把有的镜头切掉半张脸（第一版就是这么废掉的）。
   → 先用 `face_crop.py --aspect 1 --lock` 把**头位固定住**，固定裁才成立。
   （`--aspect 1` 本身不生效，真正有用的是 `--lock`。）

3. **不要靠看缩略图估时间点**。第一版按缩略图读，把雨衣中景当成了皱眉特写。
   → 抽几个关键帧逐个核对当锚点（`output/_pipeline/新素材_锚点核对.png`
      就是那张锚点对照图：5.4s 嘟嘴 / 9.5s smirk / 13.0s 大笑 /
      19.6s 皱眉 / 16.0s 雨衣中景 / 20.5s 已黑）。

> **素材长度只要够用就行**：这部片只消耗约 7s，做到 10s 左右即可，
> 做长了纯属浪费 —— 关键是**前 7 秒全是好镜头**。
> （素材不够长时代码会 `%` 循环取用，成片里会看到重复。）

## 前端页面（webapp.py）★

终端里的一切都搬到网页上点。**算法一行不动** —— 页面只是把现有脚本包了一层，
另加一层只做可视化的本地服务。

```bash
"$PY" webapp.py                 # 127.0.0.1:8760，自动开浏览器
"$PY" webapp.py --cam 1         # 换摄像头（0=集成摄像头，1=虚拟摄像头）
"$PY" webapp.py --port 9000 --no-browser
```

也可以双击 `启动网页.bat`。

页面按**监视器构图**分四块：

| 区块 | 内容 |
|---|---|
| 顶部状态条 | 模型 / BGM / 交错素材 / 算法脚本 就绪灯（越界问题不用跑到一半才发现） |
| 左栏 | **录制**（时长 / 倒数 / 开始 / 提前停止 + 进度）、画面模式（raw / sigma / chad / scan / debug）、预览视图、摄像头读数 |
| 中间 | 大画面（四角括号 + 录制倒数 / 红点叠加），下面是「实时预览 / 成品播放」切换与实时读数 |
| 右栏 | **生产线**（素材与模板参数、开始出片、6 步实时状态）、成果库（成片卡片，点一下就在中间播放） |

### 两条接线：为什么录制不能起子进程，生产线可以

这两个功能看着对称，**实现方式却必须相反**，原因都是"资源归谁"：

| | 录制 | 生产线 |
|---|---|---|
| 做什么 | 摄像头取帧 → 存成素材 | 处理已有视频 → 出成片 |
| 占不占摄像头 | **要占** | 不碰 |
| 怎么实现 | 挂进 `CameraWorker` 采集线程 | 起独立子进程跑 `slop_pipeline.py` |
| 为什么 | 摄像头**只能被一个进程打开**，起子进程会两边都抓不到帧 | 它只读文件，可以放心并行 |

**录制挂在采集线程上，还顺带保证了预览与录制严格同源**：录制的帧来源
**固定是 `clean`（录制所见）**，与当前预览视图无关 —— 否则切成「调试画面」
再录，就会把 HUD 一起录进去。

> 帧是**整帧存内存**的（1280×720×3 ≈ 2.6 MB/帧），所以有 `REC_MAX_FRAMES`
> 上限（800 帧 ≈ 2 GB）。触顶会提前收尾并照常保存，**已录部分不丢**。
> 编码跑在**独立线程**里：`save_recording` 要几秒到几十秒，
> 放采集线程里会把预览钉死（画面不动，看起来像崩了）。

**生产线的进度走 JSON 文件，不解析日志。** `slop_pipeline.py --progress <path>`
每步前后**原子写**一份状态（步骤名 / 状态 / 耗时 / 失败原因 / 产出），页面只读它 ——
项目约定是**前端不解析中文日志**（靠正则匹配中文输出，换个措辞就静默失效）。
不传 `--progress` 时流水线行为与以前**完全一致**。

「仅演练」勾选会加 `--dry-run`：几秒跑完、只验参数与步骤，
不用等几十分钟渲染完才发现素材填错了行。

### 预览有两种视图，别搞混

| 视图 | 是什么 | 用途 |
|---|---|---|
| **调试画面 · 含 HUD** | `process_frame(bare=False)` 的画布 | 确认人脸 / 姿态检测有没有生效。在模式自带效果之上再多一层状态栏、录制红点等 HUD |
| **录制所见** | `process_frame(bare=True)` 的 clean 画布 | **就是录制下来的画面**（所见即所录）。除 raw 外，各模式都会带上**自己的框与标签** |

两个视图来自**同一次 `process_frame` 调用**（同时产出 canvas 和 clean），
所以预览与录制是同一路画面、同一次检测 —— 这也正是「录制必须挂在
预览线程上」的原因，见第 1 条。

> **⚠️ 2026-09-24 起本项目是「效果 / 原画」两条路**（用户看过两种效果后定的）：
>
> | 路线 | 怎么做 | 录到什么 |
> |---|---|---|
> | **要效果** | sigma / chad / scan / debug 任一模式 | 带该模式的框、标签、线框（**烧进像素**，后期擦不掉） |
> | **要原画** | 模式切到 **raw** | 零处理，逐像素等于摄像头采集帧（仅镜像） |
>
> `bare` 现在**不再抑制**各模式的绘制 —— 那些框被视为「效果本体」
> （用户原话："直角框挺帅的"）。详见「`bare` 不再抑制绘制」一节。

### 几个刻意的设计决定（每条都对应踩过的坑）

1. **录制不能起 `record_auto.py` 子进程。**
   摄像头只能被一个进程打开。子进程方案要么先释放摄像头（预览黑屏几秒 +
   弹出一个多余的 OpenCV 窗口），要么两边都抓不到帧。所以预览和录制
   **共用同一个采集线程**。
2. **状态条自检不调 `check_launch.py`。**
   它会打开摄像头，跟预览线程抢设备（本项目里 check_launch 已经因此间歇失败过）。
   自检只做文件存在性检查。
3. **前端不解析中文日志。**
   结构化数据一律走 `/api/*`。靠正则匹配中文输出换个措辞就失效 ——
   所以验收徽章要等 `verify_*.py` 支持 `--json` 之后才点亮；在那之前如实显示
   「待接入」，**不猜**。
4. **Flask 必须 `use_reloader=False`。**
   否则模块被加载两遍，第二个进程开摄像头必然失败。
5. **画面框的宽高比跟着内容走，而且交给 JS 算。**
   预览 16:9（摄像头 1280×720）、成品播放 9:16（成片 1080×1920 竖屏），
   由 `fitStage()` 按可用空间算好再写进 style。用 CSS `aspect-ratio` 一旦被
   `max-height` 夹住，宽高比就断了，四角括号会漂到黑边里 —— 而且横竖两种朝向
   谁受限还不一样，只判一边必然错一边。

### ⚠️⚠️ 复刻时踩到的坑（重要，跨脚本抄滤镜链必读）

**`trim` 的 1 帧余量在原速场景下不会被丢弃，而是完整进入输出。**

从 `edit_slop.py` 抄来的写法是「trim 的 duration 多给 1 帧，让 fps 丢掉多余的」。
实测（真实素材，P = 0.89392s = 26.818 帧 @30fps）：

| trim 写法 | 实际输出 |
|---|---|
| `duration = P + 1帧`（0.92725） | **28 帧** = ceil(27.818) ✗ |
| `duration = P` | **27 帧** ✓ |
| `start_frame=0:end_frame=27` | 27 帧 ✓ |

`trim` 给多少帧的料，`fps=30` 就圆整出多少帧 —— **那 1 帧余量不会被丢弃**。
在 `edit_slop.py` 里无害，是因为那里 setpts 有 0.25x / 1.35x 的**强压缩**，
压缩后总长明显小于目标，多出的帧确实被丢掉了。

**症状**：硬切点相对理论边界**每镜固定 +1 帧（33.3ms）**，到快剪段第 4 镜
偏移已达 +12 帧；验证判定 "3/25 命中"、中位偏差 354.7ms。
因为偏差是**稳定匀速**而非随机漂移，极易误诊成"帧量化漂移"。

**修法**：`trim=start_frame=K0:end_frame=K0+N_OUT` 按帧数精确取料。

> **教训**：跨脚本抄滤镜链**必须重新验证**，不能假设前提成立。
> "多给 1 帧会被丢掉"是 `edit_slop.py` 的**实现巧合**，不是 ffmpeg 的通用行为。

### ⚠️ 验证脚本自身的两个阈值坑

1. **黑白镜判定阈值不能用 `<9`**。全局叠加 `rgb_split` 色差 + `noise` 颗粒后，
   真黑白镜的饱和度会顶到 **10~13**（未加特效时才是 3~8）。
   曾把镜 4（饱和度 10.7）误判成"彩色"。
   → 阈值放到 **14**，并输出"同段彩色镜饱和度中位"作参照。
   最终核对方式：**抽帧肉眼比对** —— 镜 4 与镜 6 是同一段 Bateman 抽烟画面，
   镜 4 皮肤灰白（确为黑白）、镜 6 皮肤红润（确为彩色）。

2. **理论切点不能把"每个拍边界"都算上**。铺垫段 9 拍是同一段实拍连续取料，
   **画面连续、根本无硬切**。把这 9 个边界算进理论切点会让分母虚高，
   看起来像"漏检 8 个"，其实是理论侧错了。
   → 理论切点只算**换源处**（铺垫→快剪、快剪段内部每镜、快剪→结尾）。

### 分镜效果编排（FAST_PLAN）

| 效果 | 手法 | 在表里出现 |
|---|---|---|
| **微波炉** | **同一段源**正放 + 倒放（源只消耗一次、输出两拍） | **× 6** |
| **镜像** | 单镜左右翻转，五官错位感 | × 4 |
| **缩放脉冲** | 节拍点突然放大再收回 | × 4 |
| **负片闪** | 该镜开头 0.12s 色彩反转 | × 2 |
| ~~分屏镜像~~ | 左半原图 + 右半镜像 | **× 0（已下架）** |
| ~~单拍倒放~~ | 整镜倒着放，占 1 拍 | × 0（备选编排用） |

>
> **另一版编排（备选 B）**：把上面 6 个 `boom(2)` 里的 2 个换成 4 个 `rev(1)`
> —— 总拍数仍是 22，微波炉 ×4 + 单拍倒放 ×4。**用户 2026-09-25 选了 A
> （微波炉 ×6）**，B 的产物移到了 `output/_pipeline_v2/备选B_*`。
> 换回只需把 2 个 `("boom", 2)` 换回 4 个 `("rev", 1)`。

#### ⚠️⚠️ 加新效果前必读：**逐镜滤镜可能改时序**（2026-09-24 实测，代价很大）

`zoompan`（缩放脉冲）会**按自己的 fps 重新生成时间戳、完全忽略输入 PTS**。
而快剪段的时间轴在上一步 `setpts` 里已经被压缩过（1.35x），
于是 zoompan 输出的时长是"未压缩"的 —— **整段被拉长约 1.35 倍，
它之后的所有分镜整体后移**。

这个 bug 最阴的地方是**全套验收都发现不了**：

| 验收手段 | 当时的结论 |
|---|---|
| 总帧数 / 总时长 | 562 帧、18.75s，**完全正常** |
| `verify_flash`（闪白压点） | 通过 |
| `verify_cuts`（硬切压点） | 通过（甚至报 22/23） |
| `verify_contentaware`（内容匹配） | 通过 |
| `--no-fx` 验收专用片 | **完全正确** —— 只看它永远发现不了 |

而实际成片里，**"每一格放的是哪一段源"从第一个 zoom 之后就全错位了**：
22 个 zoom 时累积错位 **+21 帧（0.7s）**，后半段整个脱离拍点。
它不报错、时长对、切点看着也压在拍上，只是画面内容悄悄换了。

**怎么抓它**：`test_slot_map.py` —— 用**纯色合成源**（实拍=纯红、素材=纯蓝）
出片，再逐格采样看 BGR 通道，与 `--dump-plan` 的逐格方案比对。
零歧义、零主观。实测：修复前 26/40 错位，修复后 40/40 全对。


### 切片密度（`--slices`）

| 值 | 每刀时长 | 分镜数 | 感觉 |
|---|---|---|---|
| `1`（默认） | 0.469s | 22 | 每拍一刀，跟着底鼓，稳 |
| `2` | 0.234s | 44 | 每半拍一刀，"切得极碎" |

调密度**不会打乱效果编排**——分镜表里的"占几拍"按比例展开成子切片，
效果类型保持不变，只是同一镜里换更多次画面。

### 全局特效

| 特效 | 实现 | 范围 |
|---|---|---|
| 硬切 | `concat` 直接拼，无转场 | 全片 |
| 闪白 | `eq=brightness` + `mod()` 周期表达式 | 仅 Drop 之后，每拍 1 帧 |
| **切换模糊** | `gblur` **空间**低通，门控在**每拍末尾**（切入前，提前 2 帧收尾） | 快剪段 |
| 轻微抖动 | `crop` 偏移 × `gte(t,drop)` 门控 | 仅 Drop |
| 色差 RGB 分离 | `rgb_split(shift=6)` 水平偏移 | 全局 |
| VHS 颗粒 | `noise=alls=14` | 全局 |
| 降饱和 / 黑白 | `hue=s=`，`--bw 0.35` | 全局（默认关） |
| 结尾淡出 | `afade` 1.2s | **仅音频**（画面是硬切，见下） |

> ⚠ **两处与早期文档不符，以这里为准**：
> 1. **切换模糊用的是 `gblur`（空间），不是 `tmix`（时间）**。`tmix` 会把切点
>    整体拖后 ~90ms（实测：模糊 4 帧 → 切点中位偏差 +92.7ms），对卡点成片是致命的。
>    旧实现保留在 `cut_blur_mode="temporal"` 分支里供对比，**不要用**。
> 2. **`--fade` 只作用于音频**（`afade`），画面没有 `fade=t=out` ——
>    最后一帧是硬切。`edit_ref.py` 那边画面/音频都有淡出，两个脚本不一致。

### 常用参数

```bash
python edit_slop.py --footage 实拍.mp4 --material 素材.mp4 \
    --slices 2          # 每半拍一刀（切得极碎）
    --bw 0.35           # 降饱和 35%（廉价感）
    --cut-blur 0        # 关掉切换动态模糊
    --flash 0           # 关掉闪白
    --no-fx             # 关掉分镜效果，回到朴素每拍一刀
    --aspect square     # 1080x1080 方形
```

> **动态模糊为什么门控在拍点末尾而不是开头**：
> 闪白已经占用了拍点开头 0.05s。两者都挤在开头会变成"又白又糊"的一坨，
> 而且 `tmix` 会把前一帧的白色拖进来，实测白帧从 1.03s 涨到 1.80s。
> 改成"上一镜末尾起拖影 → 切 → 闪白"，白帧回到 1.03s（每拍恰好 1 帧），
> 读起来也才有"过渡 → 卡点"的层次。

### 人脸特写素材（face_crop.py）

原始录像里脸只占约 **16%** 画面高，缩到竖屏后脸部信息量极低。
`face_crop.py` 用 MediaPipe 追踪人脸并放大裁切。

```bash
# 单独跑（推荐从原始分辨率版裁，见下）
python face_crop.py 新素材_原始.mp4 --zoom 1.8 -o 新素材_人脸特写.mp4

# 或直接接进成片流程
python edit_slop.py --footage 素材.mp4 --material 素材2.mp4 --face-crop 2.0
```

| 参数 | 说明 |
|---|---|
| `--zoom` | 裁切窗口高 = 人脸高 × zoom（默认 **3.0**）。人脸框只覆盖额到下巴，×3 ≈ **证件照构图**（含肩） |
| `--headroom` | 头顶留白（默认 **1.0**，给人脸高的比例） |
| `--lock` | **锁头运镜**：头部固定在画面同一位置。自动把跟踪调到最紧（alpha=1.0、死区=0） |
| `--auto-band` | 自动排除上下模糊填充条（竖屏合成版建议开） |
| `--fixed-zoom` | 退回固定窗口（**只适合人与镜头距离不变的素材**） |
| `--no-roi` | 关闭两级检测（默认开，见下一节） |

**四个关键实现点**（都踩过坑）：

1. **必须平滑轨迹 + 死区**（非 `--lock` 模式）。逐帧 bbox 抖动大，
   直接裁会疯狂晃动。死区把"微抖"直接吃掉，而不是平滑成慢速漂移。

2. **默认自适应变焦，不要用固定窗口**。
   实测人脸高在 **124~386px** 之间波动（3 倍）。固定窗口按中位数定尺寸时，
   近景帧的脸会被裁断。自适应让每帧窗口 = 该帧人脸高 × zoom，再统一缩放。

3. **必须用原始分辨率版**（见下），否则人脸像素少 29%。

4. **⚠️ 留白必须按"窗口高度的比例"算，不能按"人脸高的绝对倍数"。**
   写成 `cy = y - bh*headroom + hh/2` 时，窗口一收缩（3bh → 1.7bh），
   人脸顶+留白 = 2bh > hh → **人脸被裁断**（额头整个切掉，只剩眼睛鼻子）。
   改成 `cy = y - hh*frac_top + hh/2` 后，人脸在窗口里的相对位置恒定。

### ⚠️ 网页录制的素材是**竖屏合成版**，不是原生帧（2026-09-24 实测）

`webapp.py` 的录制挂在采集线程上、存的是 `clean` 画布 ——
也就是**已经合成好的 1080×1920 竖屏版**（16:9 摄像头画面居中 + 上下模糊填充）：

```
录制_raw_0924_082604.mp4   1080×1920
  真实画面只占 1920 行里的 ≈608 行（31.6%），上下 2/3 是模糊填充
  人脸框高 ≈162px（占 1920 的 8.5%）
  原生 1280×720 帧若落盘，同一张脸是 ≈192px —— 多 18%
```

后果：`face_crop` 只能从这个合成版裁，裁切窗口 270×480 再放大到 1080×1920
= **4.0 倍上采样**，脸偏软。**真正的杠杆不是换算法，是让脸在源画面里更大**
（坐近一点），以及**同时把原生帧落盘**（`record_auto.py --raw --raw-out` 会存，
网页录制目前不存 —— 这是个已知缺口）。

> 反过来，合成版也**不是**没有好处：人脸占画面比例小 ⇒ 锁头需要的余量小
> （实测垂直位移只有 3.4%），锁起来很稳。所以"能不能锁"和"够不够清晰"
> 是两个独立问题，别用一个结论覆盖另一个。

### ⚠️⚠️ 顺序有讲究：**先裁特写、再调色**（2026-09-24 实测）

`slop_pipeline.py` 现在的顺序是「… →（调色）→（人脸特写）→ 成片」，
也就是**先从调色版裁特写**。实测这会让锁头明显变差：

| 特写源 | 两级检测命中 | 裁切中心逐帧位移 | 输出**两眼中点**漂移 | 判定 |
|---|---|---|---|---|
| **未调色原片**（`录制_raw_0924_082604.mp4`） | **434/434（100%）** | 水平 1.55 / 垂直 0.75px | **3.2px / 2.6px** | ✓ |
| 调色版（`..._调色.mp4`） | **394/434（90.8%）** | 水平 1.52 / 垂直 0.69px | **6.3px / 10.9px** | ✗ |

> **关键点：两边的"裁切中心逐帧位移"几乎一样**（1.5/0.7px）——
> 只看这一行会以为锁得一样好。真正的原因是**检出率掉了 9%**：
> 没检出的帧走插值/保持，窗口轨迹照样平滑，但**脸相对窗口在漂**。
> 所以「轨迹平不平」和「锁没锁住」是两件事，**必须在输出上量两眼中点**。

**修法（已验证）**：先 `face_crop --lock` 从原片裁，再 `grade.py` 调色，
最后用重指向的映射表出片。实测锁头 **3.5px / 2.6px ✓**，
成片 `output/成片_人脸特写_v3.mp4`。

> ⚠ `slop_pipeline.py` 的步骤顺序**尚未改**（改它属于设计决策，留给用户定）。
> 现在的临时做法：手工 `face_crop` → `grade` → `repoint_map` → `edit_slop --clips`。
> 注意调色版的**检出率下降**本身也值得单独查（灰度/低饱和是否影响 MediaPipe）。

### ⚠️⚠️ 两个已修的静默 bug（2026-09-23，都值得记）

这两个 bug 让「人脸特写」在真实素材上**完全不可用**，而且**都不报错**。

#### bug 1：两眼中点坐标被放大 2 倍 → 裁切完全错位

```python
# ✗ 错：多除了一次 sc
ex = (lm[33].x + lm[263].x) / 2 / sc
eyes = (ex * w, ey * h)

# ✓ 对：归一化坐标直接乘原图尺寸
ex = (lm[33].x + lm[263].x) / 2
eyes = (ex * w, ey * h)
```

`lm[].x/y` 是**归一化**坐标（0~1，相对检测图）。还原到原图像素只需 `× w/h`。
写成 `(lm.x)/sc*w` 等于多乘了 `1/sc`；本素材 `sc = 640/1280 = 0.5`，
于是**坐标被放大 2 倍**。

实测（`_diag_facecrop.py`，707 帧）：

| | 与"人脸框中心"的距离 |
|---|---|
| 现行 eye（除 sc） | 中位 **686px** / 最大 886px ❌ |
| 正确 eye | 中位 **40px** / 最大 78px ✓ |

人脸框本身只有 144×176px —— 眼睛中点飞到框外 4~5 个脸宽，
裁切窗口被 clamp 到画面边缘，**裁出来全是背景**。
端到端验收：修复前 **0/742 帧**检测到人脸，修复后 **707/742 = 95.3%**。

> **教训**：混用"归一化坐标"和"像素坐标"时，先写出单位换算链
> （归一化 `--×w-->` 原图像素 `--×sc-->` 检测图像素），再检查代码走的是哪条。
> `face_bbox()` 走的是"像素→像素"（先 `×检测图宽` 再 `/sc`），所以它是对的 ——
> 同一个函数里两条路的换算方式不同，是这次出错的结构性原因。

### ⚠️⚠️ bug 3：人脸占比太小时，检测会**静默失效**（2026-09-24）

症状：素材画面看着完全正常（姿态能稳稳检出、鼻/眼/耳可见度 0.99），
但 `face_crop` 报 **0/434 帧检出人脸**，输出只是把画面中心裁一刀 ——
**不报错**，肉眼也很难一眼看出"这张脸没被识别"。

一开始怀疑是调色的影响。答案是**不是**：检测在调色之前
（`sigma_realtime.process_frame` 里：147 镜像 → 154 缩到 640 → **170 检测** →
193 才 `render_mode` 调色），所以调色不可能影响它。

**真正的原因**：MediaPipe 的人脸检测器看的是**脸占画面的相对比例**，
不是绝对像素。于是提高分辨率完全无效：

| 检测图宽度 | 512 | 640 | 800 | 960 | 1080 | 1280 |
|---|---|---|---|---|---|---|
| 检出率 | 0/44 | 0/44 | 0/44 | 0/44 | **0/44** | 0/44 |

因为检测器内部总要把输入缩到它固定的输入尺寸，**等比缩放不改变比例**。
放低置信度门槛（`detection`/`presence` 到 0.1）也只从 0/44 变 3/44，是噪声级。

实测门槛大致在 **2%**：

| 脸高占画面高度 | 检出率 |
|---|---|
| **1.5%** | **0%** ← 镜头拉得远，画看着正常 |
| 2.3% | 79% |
| 5.4% | 80% |

**解法：两级检测**（先粗定位、再放大）。姿态模型在脸很小时仍能稳定给出
鼻(0)/眼(2,5)/耳(7,8) 的位置，于是用它们框出脸、裁出来放大到 640 再检：

```
整图检出率 < --roi-below(0.35)  →  自动切到「姿态定位 ROI → 裁出放大 → 再检」
```

实测救回效果：

| | 整图 640 | 两级检测 |
|---|---|---|
| 检出率 | **0/434（0%）** | **434/434（100%）** |
| 裁切窗口占画面 | 90%（等于没裁） | **27%**（真证件照构图） |
| 裁切中心位移 | x 540–540（**完全不动**） | x 522–706（真锁头跟随） |

对照组不受影响：`080343` 99.6%、`新素材_原始` 95.3% 都**不触发**升级。
`action_detect.py` 也做了同样处理 —— 那里的意义更大，见下一节。

> **教训**：这类失效**没有错误、没有告警**，只有"结果不对"。凡是检测类模块，
> 都应该**把命中率打印出来**，并对异常低的值**显式告警**，而不是静默降级。
> `face_crop.py` 现在在检出率 <20% 时会打出一段 `!!!` 框起的提醒。

### ⚠️⚠️ bug 4：特征缓存不校验来源 → 换素材出片时复用别的素材（2026-09-24）

这是目前为止**最严重**的一个：`action_detect` 的缓存原来是**固定路径 + 不校验
它来自哪个视频**，而流水线的缓存路径写死为
`output/_pipeline/动作分析/features.npz`。于是：

```
第 1 次出片（素材 A）  →  写入 A 的特征
第 2 次出片（素材 B）  →  静默复用 A 的特征
```

现场数据：

| | 帧数 | fps | 人脸命中 |
|---|---|---|---|
| 流水线在用的缓存 | **429** | 28.56 | **88.3%** |
| 实际出片素材 `082604` | **434** | 28.88 | **0%** |

（429 帧 / 88.3% 正好对上另一段素材。）后果是**锚点位置属于另一段素材**，
内容感知在本素材里找不到任何峰值 → 大面积走钳位兜底 → 同一帧被反复取用，
也就是用户看到的「同一个拧水瓶动作连续回放四次」。

修法（双保险）：
- `save_cache` 写入源文件指纹（绝对路径 + 大小 + mtime），`load_cache` 比对，
  不符就丢弃重提并**明确打印**"缓存来源不符"
- `slop_pipeline.step_detect` 的缓存名改成按素材路径哈希 `features_<hash8>.npz`，
  避免不同素材互相覆盖、也避免交替出片时反复重提取

> **教训**：**任何**缓存中间产物都要带"它属于哪个输入"的信息并在读取时校验。
> 固定路径 + 不校验，出问题的方式是**完全静默**——事件列表照出、切片照成、
> 渲染照跑，只是内容与素材无关。

#### bug 2：反射填充量写死 35% → 切片越界，报错误导

```python
# ✗ 错：固定比例，不随轨迹变化
PAD = int(H * 0.35)

# ✓ 对：按窗口实际需要伸出去多少
pad_top = max(0, -min(y0 for _, y0, _, _ in crops))
pad_bot = max(0, max(y0 + hh for _, y0, _, hh in crops) - H)
PAD = max(PAD, pad_top, pad_bot) + 8
```

窗口位置由人脸轨迹决定，可能向上超出画面很多。本素材 `y0` 低到 **-320**，
而 35% 只有 252px → `y0 + PAD = -68` 是负数 → numpy 负索引从数组末尾倒数，
切出**空数组** → `cv2.resize` 抛 `(-215:Assertion failed) !ssize.empty()`。
修复后动态填充 **328px**（轨迹需要 上320 / 下133），742/742 帧全部正常输出。

> ⚠ **这个坑是在修好 bug 1 之后才暴露的**：之前裁切中心被错误地算到画面
> 右下方，`y0 min = 34` 恰好为正，越界被错误的位置掩盖了。坐标一修对，
> 窗口上移到正确位置，`y0` 变负，问题才现形。
> **修一个 bug 常常会暴露被它掩盖的另一个 bug** —— 修完必须**端到端重新跑**，
> 不能只看那个 bug 的指标变好就收工。

#### 顺带加的两道防线

1. **切片前显式越界检查**。不要依赖 numpy 切片的"宽容"行为 ——
   负起点会被当成"从末尾倒数"，切出空数组或错位区域且**不报错**，
   一直到 `cv2.resize` 才抛出完全指不到根因的错误。
   现在越界会**明确报错并指出帧号/PAD/窗口参数**。
2. **新增 `verify_facecrop.py`**（客观验收）：在**输出视频**上重跑人脸检测，量
   - 人脸命中率（裁偏时会暴跌）
   - 人脸位置（归一化坐标，应落在中央区域）
   - 人脸占画面高度比（特写的意义所在；原始素材约 16%）
   - 人脸逐帧位移（锁头效果）

   修复版实测：命中率 **95.3%**、位置 100% 在画面内、占画面高 **33.4%**、
   逐帧位移中位 **0.71px**。

   > **为什么必须有这一层**：中间变量全对但最终画面错的情况真实发生过 ——
   > 上面两个 bug 里，日志打印的"裁切中心范围 x 786-1174"**看起来是合理数字**，
   > 不与人脸位置对照就发现不了。只有回到最终画面量"脸到底在不在"才可靠。

### ⚠️ 锁头运镜的两难，以及反射填充这个解法

「锁头」（头部固定在画面同一位置）和「证件照构图」（窗口要大）**本质冲突**：

- 人脸中心在画面里纵向移动 **183→360px**（实测）
- 要让窗口**任何一帧都能居中人脸**，窗口高必须 ≤ `2 × min(183, 720−360) = 366px`
- 但证件照需要窗口 ≈ `3 × 人脸高 = 642px`
- **366 < 642 —— 二选一**

**解法：给源画面做反射填充**（`cv2.copyMakeBorder` + `BORDER_REFLECT_101`），
上下各填 35% 画面高。窗口就能伸到原画面之外、**永远居中**。
反射区落在人脸之外（头发/背景的镜像），且只在人脸贴边时才用到。

> **实测效果**（`probe_lock.py`，在成片上重跑人脸检测量漂移）：
>
> | 配置 | 头占画面 | 水平漂移 | 垂直漂移 |
> |---|---|---|---|
> | 当前默认 alpha=0.12 | 35.7% | **83.9px** | 141.9px |
> | **`--lock`** | 35.5% | **5.8px** | 靠填充解决 |
>
> 水平方向从 83.9px 降到 5.8px（接近半屏 → 几乎不动）。

> **为什么必须在成片上量**：参数看着合理不代表头真的锁住了。
> `probe_lock.py` 在**输出视频**上重新跑人脸检测，量头部位置的标准差 ——
> 这是唯一能验证"锁头"的方法。

### 锁头运镜（lockhead.py）

把头部**钉死在画面固定位置**、背景绕着头转。与 `face_crop.py` 的区别：

| | `face_crop.py` | `lockhead.py` |
|---|---|---|
| 做法 | 裁切窗口跟随人脸 | **相似变换**（平移+旋转+缩放）作用在整帧上 |
| 锁定精度 | 水平 ~4px / 垂直 ~31px | **残差 0.0000px** |
| 边角处理 | 反射填充补边 | **解析求解放大量 k**，保证不露黑边 |
| 旋转补偿 | 无 | 有（`--rot-strength`） |
| 成本 | 无额外放大 | 头动得越多，k 越大（会掉分辨率） |

```bash
python lockhead.py 素材.mp4 锁头后.mp4 --lock-point eyes --debug-dir debug
python measure_lock.py 锁头后.mp4        # 独立验收
```

参数直接对应剪映的「主体锁定」：`--rot-strength`（旋转强度）、
`--size-strength`（保持主体大小不变）、`--anchor`（头部落点）。

**四步算法**：
1. **找头** — YuNet 人脸检测（用双眼关键点算头倾斜角）；`--mode lk` 走
   Shi-Tomasi 角点 + 光流 + `estimateAffinePartial2D`（背影/遮挡也能跟）
2. **修轨迹** — 缺失插值 → 中值去野值 → **对称高斯平滑（非因果，零滞后）**
3. **解变换** — 相似变换把头部精确映到锚点，平移量反解 → **锁定残差恒为 0**
4. **算放大量 k** — 把画布四角反解回源图、要求仍在源内，逐角点解 k 的下界；
   **k 取全场常数**，避免抽动感

> **⚠️ 这条路的成本取决于素材本身**。实测我们那段素材：
> 头部在 720px 高的画面里**移动了 273px** → 要完全锁住需要 **4.26 倍放大**
> （超过默认上限 3.0 → 56 帧露黑边），而且 4.26x 意味着有效分辨率只剩 300px 宽。
>
> **这不是算法问题** —— 任何正确的锁头都需要这个放大量。拍摄时的对策：
> - **左右留 15%~20% 余量**（给补偿留空间）
> - 动作幅度别太大（尤其别大幅度前后/上下移动）
> - 高分辨率拍、低分辨率出（4K 拍 1080 出更稳）
> - 高速甩镜的**滚动快门果冻感 2D 变换补不回来**，这类镜头不适合锁头

#### ⚠️ 上面那个 4.26x **不是通用结论** —— 它只属于那段素材（2026-09-24 更正）

`273px / 4.26x` 是在 **`新素材_原始.mp4`（1280×720 / 25.01s / 09-23 录的）**
上量的。把它当成"我们这个机位就是锁不了"来用是错的 ——
换一段素材结论会完全不同：

| 素材 | 分辨率 | 人脸框中心位移 | 锁头放大下界 k | 判定 |
|---|---|---|---|---|
| `新素材_原始.mp4`（09-23） | 1280×720 | 水平 26.6% / **垂直 42.0%** | ≈1.7~4.3x | ✗ 余量超了 |
| `录制_raw_0924_082604.mp4`（09-24） | 1080×1920 | 水平 **15.0%** / 垂直 **3.3%** | ≈**1.45x** | ✓ 达标 |

也就是说 **09-24 那段素材本来就够用**，不需要重录 ——
按老结论去重录属于白忙。所以"能不能锁"必须**每段素材单独量**：

```bash
"$PY" probe_headroom.py output/录制_raw_0924_082604.mp4        # 素材体检
"$PY" probe_headroom.py output/成片_人脸特写_v2.mp4 --eyes-only  # 锁定验收
```

`probe_headroom.py` 读**视频或特征缓存**都行（缓存模式秒出），
内部走与 `face_crop` 相同的两级人脸检测。

#### ⚠️⚠️ 验收指标必须与**锁定点**同口径（否则结论会整个反过来）

`face_crop --lock` 锁的是**两眼中点**（见下一节）。如果用 `probe_lock.py`
的**人脸框中心**去验它，量到的是「框中心 vs 两眼中点」的相对摆动
**被裁切放大 4 倍后**的结果 —— 那不是锁定残差：

| 同一份输出 `人脸特写_锁头.mp4` | 水平 std | 垂直 std | 判定 |
|---|---|---|---|
| 量**人脸框中心**（probe_lock 口径） | 38.7px | 6.0px | ✗ 不合格 |
| 量**两眼中点**（锁定点口径） | **3.2px** | **2.6px** | ✓ 合格（<10px） |

同口径的前后对比（都用两眼中点、都归一化到 1080×1920）：

| | 水平 std | 垂直 std |
|---|---|---|
| 源素材 `录制_raw_0924_082604.mp4` | 36.7px | 17.0px |
| 锁定后 `人脸特写_锁头.mp4` | **3.2px** | **2.6px** |

—— 水平漂移降到 **1/11**，人脸占画面高 **33.7%**。**这段素材的锁头是成功的。**

而且这次和 README 上面那条教训**方向相反**：那边是"锁定框中心、框中心自然
占便宜"，这边是"锁两眼中点、框中心自然吃亏"。同一条原理：
**指标和锁定点不一致，量到的就不是你想验的东西。**

> 另外 `probe_lock.py` 的 `CASES` 是**写死的文件清单**（`output/_lock_完全.mp4`
> 等），那批文件早就不在了，所以现在跑它只会得到一排"(缺文件)"。
> 要量成片漂移用 `probe_headroom.py --eyes-only`。

### 从 lockhead.py 移植进 face_crop.py 的两个技术

1. **非因果平滑（对称高斯）**。原来用 EMA（因果滤波）**必然带相位滞后**——
   头动得越快滞后越大。但整段视频都在手上，完全可以"看到未来"，
   对称高斯核群延迟为 0，**平滑掉抖动的同时零滞后**。
2. **两眼中点作为锁定点**。框中心会随下颌/额头的检测抖动而晃，
   双眼位置由眼眶骨骼决定，稳得多。

> `--smooth-sec` **不是开关而是一条取舍曲线**（实测数据来自 lockhead 的 README）：
> 0 = 头钉死但背景带检测噪声抖（33.9px/帧）；
> 0.25 = 背景顺了但头漂到 10px；**折中点 0.06**（已设为默认）。
>
> 另一个教训：他们最初只测「人脸框中心」，而锁定框中心自然占便宜；
> 补测「两眼中点」后结论才站得住 —— **验收指标选什么，会影响你选哪个锁定点**。

### 自动录制（record_auto.py）

`sigma_realtime.py` 是交互式的（要按 R），自动化流程里没法用。
`record_auto.py` 倒数后自动录 N 秒。**录到什么取决于模式**：

```bash
# 要原画（后期 grade.py 调色用）—— 零处理，逐像素等于摄像头画面
python record_auto.py --raw --secs 25 --countdown 5 \
    --out output/新素材_原画.mp4 --raw-out output/新素材_原始.mp4

# 要效果 —— 带该模式的框与标签（sigma：暖色方框 + 金角框 + 标语）
python record_auto.py --mode sigma --secs 25 --countdown 5 \
    --out output/新素材_sigma.mp4
```

同时产出**竖屏合成版**（剪辑用）和**原始分辨率版**（人脸特写用）。
⚠ 不带 `--raw` 时画面**带框**，烧进像素、后期擦不掉（见下两节）。

> ⚠ 内部踩过的坑：`dur`（录制时长）**必须在释放 MediaPipe 资源之前算**。
> 写在 `face_lm.close()` 之后会把清理时间（实测 80+ 秒）也算进去，
> 于是 63 帧被当成 87.4s、算出 0.7fps，导出成 8fps 慢放。
> 真实每帧只要 41-119ms（约 20-29fps）。

### ⚠️ HUD 是烧进像素的，擦不掉 —— 必须从源头不画

录像里的 HUD（人脸框、状态栏、底部文字）**烧死在像素里**。试过
「选金色像素 + inpaint」擦除角标，**结论是不可行**：

- 颜色判据极易写错通道（`SIGMA_GOLD` 是 BGR，写成青色范围会一个都选不中）
- **改对之后更糟**：sigma 模式给整张脸加了暖金色调，**脸本身就落在"金色"范围内**，
  掩膜会把整张脸涂掉，inpaint 后脸上出现大片色块

**根本原因：要擦的东西和被保护的东西颜色相近，无法靠颜色区分。**

**正解：录制时就不画。** 2026-09-24 起这条统一由 **raw 模式**承担 ——
「画面模式」切 raw，或 `record_auto.py --raw`（= `--no-grade`）。

> ⚠ 别再指望用别的模式"录干净素材"：各模式的框与标签现在是**刻意的效果**，
> 已不再受 `bare` 抑制（见下一节）。

> 手上只有带 HUD 的旧素材时，可用 `--safe-y 702:1161`
> （本机录像的实测 HUD 边界）把裁切框限制在 HUD 之间。
> 代价：下巴会被切掉一点、裁切框纵向失去跟踪能力，
> 而且**横向的角标仍会入镜**（安全带只管纵向）。

### ⚠️ `bare` 不再抑制绘制 —— 「效果 / 原画」两条路（2026-09-24 回滚）

这一节的结论**被用户推翻过一次**，过程留着，因为踩的坑有普遍性。

**第一版（已废）**：`bare` 只抑制框和文字，模式的调色照旧生效 ——
于是 sigma + bare 仍然压暗、脸上仍有暖色，用户会问
"我选了『录制所见』，脸上怎么还有色差？"。当时的解法是引入 `raw` 模式
（零处理），并把 `bare` 定位成"该模式的裸版"。

**第二版（当前）**：用户看过硬边矩形框与羽化椭圆两种效果后，
**要了硬边的那个**（原话："直角框挺帅的，椭圆怪怪的"）。
于是 `bare` 的抑制被**整体回滚** —— 各模式自己的框 / 标签 / 线框
不再受 `bare` 控制，它们被视为**效果本体**。

所以现在只有两条路，选错就白录：

| 路线 | 怎么做 | 录到什么 |
|---|---|---|
| **要效果** | sigma / chad / scan / debug 任一模式 | 带该模式的框、标签、线框（**烧进像素**，后期擦不掉） |
| **要原画** | 模式切到 **raw**（`record_auto.py --raw` / `--no-grade`） | 零处理，逐像素等于采集帧（仅镜像） |

实测逐像素差异（`probe_raw.py`，拿参考片当干净底子）：

| 设置 | 平均差 | 最大差 | 录到什么 |
|---|---|---|---|
| `raw` | **0.00** | **0** | 逐像素恒等（**唯一**零处理） |
| `debug` | 8.23 | 255 | 青色人脸线框 + 绿色骨架 |
| `sigma`（默认） | 19.36 | 250 | 暖色方框 + 金色角框 + 标语 |
| `chad` | 115.47 | 255 | 方形黑白高对比 + 两行标语 |
| `scan` | 22.83 | 255 | 绿调 + 网格 + 锁定框 + 读数 |

> `debug` 那行是**回滚生效的判据**：回滚前它在 `bare` 下是 0.00
> （那时 `--no-grade` 借 `debug + bare` 来录原图），现在线框回来了所以非 0。
> 同时 `--no-grade` / `--raw` 已改走 `mode="raw"`，不再借 `debug`。

**传输/编码环节要另算** —— 它不是"处理"，但会让"你在网页上看到的"和
"文件里的"对不上：

| 环节 | 平均差 | 最大差 |
|---|---|---|
| 网页预览（JPEG quality 78） | 1.33 | 30 |
| mp4 导出（yuv420p 色度抽样） | 0.29 | 8 |
| PNG（无损） | 0.00 | 0 |

所以：网页预览本身带 JPEG 压缩（量级 1.3/255，比 sigma 的 19.4 小一个数量级，
但严格说不是逐像素原画）；mp4 也必然经过 yuv420p 色度抽样。
**要零损失的原画存档，导出无损格式（PNG 序列 / ffv1）。**

**为什么不再让 `bare` 兼职**：一个开关只该表达一件事。
"不画框"和"不调色"叠在一起，就会有人（包括我自己）以为 `bare` 等于原图，
然后录出一份带着调色的素材。现在职责分得很干净：
**要干净 = 选 raw；要效果 = 选别的模式。**

> **实现上有个只有实测才抓得到的坑**：`render_mode` 的 raw 分支必须写
> `return orig.copy()`，**不能 `return orig`**。
> `process_frame` 里 canvas 与 clean 是**两次独立调用**的返回值，若两次返回
> 同一个 ndarray 对象，随后 `hud(canvas, ...)` 的**原地绘制会同时改到 clean** ——
> 于是"原图模式"录出来带着状态栏文字。实测症状：与采集帧平均差 **13**、
> 最大差 **252**（那是白色文字像素），而 `debug` 分支因为写的是 `orig.copy()`
> 所以一直正常，**代码看着完全合理**，只有跑探针才会暴露。

> **验证工具**：`probe_raw.py` —— 打印每条录制路径与原画的逐像素差，
> 并存一张 `原画 / raw / sigma` 的三联对照图到 `output/_probe_raw/`。

> **📌 待办**：把"带框"正式做成一个模式（与 raw 并列），并打磨那个框的效果。
> 详见 `交接_新对话.md` 的「建议的下一步行动」。

### ⚠️ 暖色矩形：硬边 vs 羽化 —— 最后**选了硬边**（2026-09-24，改过两次）

> **结局先说**：这一节描述的"羽化修复"**已被回滚**。用户看过两种效果后
> 选了硬边矩形（原话："直角框挺帅的，椭圆怪怪的"）。下面完整保留过程与
> 实测数据，因为将来做「带框」模式时要参考 —— 但**当前代码是硬边贴法**，
> 撤掉的 `_warm_mask()` / `_WARM_MASK_CACHE` 已从源码移除。

`render_mode` 的 sigma 分支原来写的是：

```python
warm = warmify(face_crop)          # R x1.27 / B x0.78 的暖色 LUT
dark[y:y+bh, x:x+bw] = warm        # ← 整块矩形直接贴
```

人脸 bbox 的四条直边上因此是一个**突变**。实测（`probe_warm.py`，拿参考片当干净底子）：

| 对象 | bbox 边界台阶 | 同帧全图自然梯度 |
|---|---|---|
| 输入（参考片原帧） | 3.67 | 3.17 |
| `debug + bare`（`--no-grade` 录到的） | 3.67 | 3.17 |
| `sigma + bare`（默认模式录到的） | **23.58** | 3.11 |

注意暖色偏移的量级其实不大（bbox 内 15.3 vs 外面 16.4）—— **刺眼的是那条不连续**。
脸小的时候看不出来，一放成人脸特写就是明晃晃一张"暖色贴纸"。

**改法两层，只做第一层会更糟**：

1. 权重从矩形换成**羽化椭圆**（`_warm_mask`：中心 1、bbox 边界 0、smoothstep 过渡）
2. 混合的底取 `dark[...]`（**已暗化的底图**），而不是未暗化的原图

第 2 层才是关键：椭圆之外权重为 0 时，结果**恒等于周围像素**，边界处不可能有台阶。
如果只羽化暖色、底仍取原图，边界会变成"原图 vs 暗化图"的突变，比原来还差。

修完实测 **边界台阶 23.58 → 2.15**（比输入的 3.67 还低，因为暗化本身会压缩对比，
3.67×0.55≈2.0），已经等同于自然梯度。中心权重仍是 1，脸上暖色的观感与原来一致。

开销：羽化混合 0.68ms（旧写法 0.09ms），**净增 0.59ms**；sigma 端到端
**25.9 fps**（debug 36.8 / chad 29.2 / scan 17.7，均含 MediaPipe 检测），没有回归。

> **验证工具**：`probe_warm.py` —— 可复跑，直接打印边界台阶数字，
> 并把人脸周边放大 3 倍存图。前后对照图在 `output/_probe_warm/`。

### 动作驱动剪辑（完整工作流）

**录视频 → 自动动作检测 → 摘出动作片段 → 套进模板 → 生成视频**

slop 的"难绷"之处在于 —— **把无意义的动作剪得很燃**。
纯按拍点切是"节奏对但内容随机"；如果切点正好落在"举手""喝一口""傻笑"上，
荒诞感会成倍放大。所以先把动作找出来。

### 1. 检测（action_detect.py）

```bash
python action_detect.py 素材.mp4 -o 动作.json
python action_detect.py --list          # 列出可检测的动作
```

**14 种动作**，来自三条独立信号：

| 信号源 | 能测什么 |
|---|---|
| 人脸关键点（478 点） | 抬头 / 低头 / 转头 / 凑近镜头 / 后退 |
| **表情系数（52 个）** | 微笑 / 张嘴 / 眨眼 / 挑眉 / 嘟嘴 |
| 姿态关键点（33 点） | 举手 / 双手举 / 摸头 / 手到嘴边 / 耸肩 |

> 表情系数来自 MediaPipe 的 `output_face_blendshapes`，**默认是关的**，
> 本脚本显式打开。之前项目里只用了人脸框，等于白扔了 52 个系数。

**三个设计要点**：
1. **特征归一化到"人脸高度"为单位** —— 否则人一凑近，所有像素距离都变大，检测器全乱
2. 事件做**滑动平均 + 最小时长 + 冷却** —— 否则逐帧噪声会切出一堆 1-2 帧的假事件
3. 丢失检测时**保持**而不是清零

特征提取是唯一昂贵的一步（25s 素材约 1 分钟），所以缓存到 npz：

```bash
# 首次：提取 + 存缓存 + 打印信号分布
python action_detect.py 素材.mp4 -o 动作.json --stats

# 之后调阈值/调动作定义都是秒级（读缓存，不重新提取）
python action_detect.py 素材.mp4 -o 动作.json
python action_detect.py 素材.mp4 --refresh --stats   # 强制重提
```

#### ⚠️⚠️ 三个已修的检测坑（都会**静默**出错，值得逐条记）

**坑 1：有效性判据用"窗口均值"，单帧污染挡不住**

负阈值信号 `wrist_head = -dmin`（dmin = 手腕到鼻的距离/脸高）**真值必然 ≤ 0**。
检测丢失的帧被补成 `0.0`，而 `0.0 > -0.85` —— 于是"这帧没检测到手"反被判成"手在头上"。

旧实现用 `valid[i:j].mean() >= 0.5`，**允许最多 49% 的无效帧混进区间**，
只要有一帧补零，`peak = max(sig[i:j])` 就被拉成 0.0。
症状：`摸头` 事件强度 = **0.00**，而任何真实测量都不可能是 0.00。

修法：`valid` 必须是**逐帧掩码**，无效帧直接**截断**区间（`mask = (sig > thr) & valid`）。
修后 `摸头` 强度变成 -0.43 / -0.58 / -0.44 ✓

**坑 2：三个动作的阈值**永远不可能触发****

`耸肩` 阈值写 0.95，但信号 `-(肩到鼻的竖直距离/脸高)` **恒为负**，最大值才 -0.31 ——
这个动作永远不会出现，而它不报错，很容易被当成"素材里没做"。
`双手举`（阈值 0.10 / 信号范围 -3.86~-0.33）、`张嘴`（阈值 0.25 / 范围 -0.02~0.21）同理。

修法：**表情类信号一律做基线校正**（减本人的静止中位数），阈值作用在"相对自己的增量"上；
`耸肩` 改 rel + 0.70。几何类信号**不**做校正 —— 它们以脸高为单位、跨人可比，
再减基线会把阈值语义搞乱（wrist_head 的基线是 -3.1，减完 -0.85 会变成"恒真"）。
修后 10 个动作全部可触发：**49 个事件 / 14 类**（修前 43 个 / 12 类，且 `张嘴` `耸肩` `双手举` 恒为 0）。

**坑 3：表情 blendshape 因人而异，绝对值阈值不能跨人用**

`微笑` 用绝对阈值 0.45 时，有人中性表情就在 0.4~0.5，
于是**整段静止的脸被判成一次 4.7 秒的微笑**。

> 但这一条要小心：修完之后 4.72s 的微笑**依然存在** —— 抽帧核对发现
> 前 4.7 秒人确实在笑（t=0.5 那帧就是笑脸），而信号在 t=5.2 掉到 0.000，
> 是因为**手/物体正好挡住了嘴**，MediaPipe 的 blendshape 在嘴部被遮挡时会塌陷。
> 所以这不是误判，而是**已知限制**：遮挡会截断/漏检表情事件。
> 长期事件的处理方式不是调阈值，而是**记录峰值时刻**（`peak_t`）供切点吸附用。

#### 阈值标定工具（calibrate_actions.py）

上面坑 2 是靠它发现的 —— **它的价值就是让"永远不可能触发"这种错误一眼可见**：

```bash
python calibrate_actions.py                    # 全部动作 + 分位数扫描表
python calibrate_actions.py --actions 微笑,张嘴,耸肩
```

每个动作会打印信号取值范围、当前阈值是否落在范围内，以及
`p50/p70/p80/p90/p95/p97/p99` 各分位点对应的事件数 / 最长时长。
阈值该定在"只有 5% 时间超过它"那种位置，分位数直接表达了这件事。

### 2. 摘片段（clip_extract.py）

```bash
# 摘片段 + 按动作分目录 + 拼一条动作素材带
python clip_extract.py 素材.mp4 动作.json -o clips/ --by-action \
       --pad 0.20 --reel clips/素材带.mp4 --crf 16

# 只要最强的 12 个 / 只要特定动作
python clip_extract.py 素材.mp4 动作.json -o clips/ --top 12
python clip_extract.py 素材.mp4 动作.json -o clips/ --actions 举手,微笑
```

产出：`clips/<动作>/<序号>_<动作>_<起始秒>.mp4` + `manifest.json`
+ `素材带.mp4` + `reel_map.json`（含每个动作峰值在**素材带坐标**和**原片坐标**下的时刻）。

#### ⚠️ 必须去重：不去重的话"片段数"是虚的（`--dedup`，默认 partition）

同一瞬间常被多个检测器同时命中（举手 + 转头 + 微笑 + 摸头…），各切一片，
于是**同一段画面被切成好几个"不同素材"**：

```
实测（--dedup none）: 43 个片段、合计 39.87s，合并去重后**只覆盖 16.71s**
   例：5.36 / 5.39 / 5.43 / 5.46 / 5.53 / 5.53 六个片段全落在 0.17 秒内
--- 去重后 ---
--dedup partition: 22 个片段、合计 18.32s、重叠率 **0%**（时间轴的一个划分）
```

`partition` 用扫描线把时间轴切成初等区间，每段归属**强度最高**的那个动作 ——
无重叠、无遗漏、每个时刻唯一归属，是一份真正能当素材池用的清单。
另有 `--dedup greedy`（按强度贪心保留、丢弃重叠的，宁可留空白）。

> 片段里的 `peak_t`（峰值时刻）是**给剪辑器用的**：长事件（一次 4.7 秒的微笑）
> 当素材没意义，但它的峰值时刻正是切点该压住的那一帧。
> 超长区间用 `--max-dur` **等分**而不是截断 —— 等分不丢内容、可预测。
> 但 `peak_t` 只留给**真正包含它的那一块**，否则会凭空造出一堆假锚点。

> ⚠ 素材带是**从原片一次性拼**的（每个区间 trim 一次再 concat），
> 不是把切好的片段再 concat 一遍 —— 后者是"解码→编码→再解码→再编码"，白多一代损失。

### 3. 内容感知取段（`--clips`）★

到这里才真正用上前面两步的产出。**取段逻辑从"顺序游标"换成"内容池 + 动作峰值"**。

**两条模板都已支持**（助手函数在 `content_aware.py`，两边共用同一套：

| 模板 | 命令 | 段落结构差异 |
|---|---|---|
| 复刻版 | `edit_ref.py --clips 映射表.json --material 参考片.mp4` | 铺垫段 9 拍连续长镜；快剪段硬切、每镜 0.894s（1.0x） |
| 卡点版 | `edit_slop.py --clips 映射表.json --material 素材.mp4` | 正常段 17 拍 + 慢放那拍（连续源 8.086s）；快剪段每镜源消耗 `0.469×1.35=0.633s` |

> ⚠ 卡点版接内容感知时最容易搞错的一点：**`od` 要用「源消耗」不是「输出时长」**。
> 用输出时长会让窗口整体偏小 1.35 倍，"峰值落在镜内 35%" 实际变成落在源里 26%，
> 画面上峰值明显偏前。但 **`peak_pos` 不用换算** —— 整窗被均匀压缩，
> 源里 35% 处的帧在输出里仍在 35% 处。

```bash
python edit_ref.py --clips clips/reel_map.json \
       --material "2022年的剪辑 belike.mp4" \
       --aspect vertical --out 成片.mp4 --dump-plan 成片.plan.json
```

**改之前**：实拍侧就是一个**顺序游标** `t_in`，从 0 秒起一段接一段往下推，
取料公式 `t0 = t_in % max(avail - 源长, 0.05)`。三条特征：连续、单调、**与画面内容无关**。
录 25 秒只用前 16 秒，后 8.9 秒一帧没进片；而快剪段每镜只有 0.894s，
顺序取到的大概率是"手还没抬起来"或"动作已经做完"的空档。

另：复刻版已支持 `--face-crop [ZOOM]`（人脸特写前置，与卡点版同名参数），
它比卡点版多一道**时序校验** —— 特写片与原片时长差超过 1 帧就直接终止，
因为峰值坐标全部基于原片时间轴，带错位渲染等于白做。


**改之后**，两段分别处理：

| 段 | 做法 | 为什么 |
|---|---|---|
| 铺垫段 | **整段平移**到某个起始位置；位置按「它给快剪段**留下**什么」择优 | 参考片的铺垫段是**连续长镜**；逐镜吸附会把它变成 9 个跳接，「铺垫」的观感全毁 |
| 快剪段实拍位 | 在铺垫段**之外**的空档里挑峰值，**每类动作只用一次**，按时间顺序分配 | 快剪段本来就是硬切，**没有连续性约束**，那就该把最好的动作都用上 |
| 结尾 | 优先紧跟最后一个锚点；那里被占住时退到别的空档 | 它本来就是「取一段淡出到黑」，从哪段取不影响观感 |

几个必须说清楚的实现点：

1. **先按可行域筛，再按强度挑**（顺序不能反）。
   入点 `p = 峰值 − 0.35×镜长`，要求「窗口整段落在某个空档里」，
   反解出峰值必须落在 `[空档起 + 0.35×镜长, 空档止 − 0.65×镜长]`，
   再要求两两间隔 ≥ 镜长。**在可行集合里挑最强的 —— 落位必然精确，不需要任何钳位。**
   > 反过来做（先挑最强、再按时间摆）实测会吸到铺垫段已占用的峰值，
   > 报告里出现 **-10244ms** 这种荒唐的落位偏差，末镜还越界。
2. **必须给结尾段留出空档**。不留时最强的峰值会一路挑到原片末尾，
   末镜结束在 23.57s、结尾还要 1.788s → 25.36s > 原片 25.01s，结尾被挤出界。
   现在由 `_spans_for_intro()` 在最后那段空档的尾部预留 `reserve`，
   结尾段再由 `_free_gaps()` 找空档落下。
3. **铺垫段两侧都能放锚点**（`_spans_for_intro`）。
   旧实现写死了「锚点必须在铺垫段之后」—— 那只是当初顺序放置自然形成的结果，
   **不是设计约束**。失效场景很明确：素材开头就是最精华的一段时，铺垫段必然整段吃掉它。
   > 实测本片「两侧放开」与「只放之后」**打平**（都是 7 种）——
   > 所以不是靠它取胜，只是把这条人为约束去掉了。
4. **`眨眼`排到最后用**（`WEAK_ACTIONS`），不是剔除。
   眨眼只有 0.03~0.13s，切上去观众什么都看不出来，但它强度 0.4~0.5 并不低，
   纯按强度排会挤掉真正有戏的动作。排到后面而非剔除：池子够用时永不选它，
   不够时还能兜底，不会让某些镜因为「没候选」退回顺序取用。
5. **每类动作只用一次，凑不满时优雅复用**（两轮选择）。
   第一轮只接受「该类型第一次出现」的峰值，第二轮才放开重复补齐；
   复用挑的是**离同类上一次最远**的那一对 —— 同一种动作出现在相邻两镜里，
   观感就是「怎么又是这个」，隔着好几秒再用一次几乎察觉不到。
6. **兜底必须避开已用位置**（`fallback_in_pt`，2026-09-24 修）。
   候选峰值不够时，旧实现是 `ca._clamp_free` 把入点「钳进空档」——
   而空档只剩一个时，**所有**剩余的镜头位都会被钳到**同一帧**上。
   实测（单段 15s 素材）：11 个实拍位只有 **5 个不同入点**，最高频出现 **7 次**，
   成片里就是"同一个动作连续回放好几遍"（用户原话），
   而报告只写一句「退回顺序取用」，**看着像素材动作不够**。
   现在三级降级：最宽空档顺延 → 全占满时取离已用最远 → 最后才钳位。

   > **量化判据**：数不同入点的个数。修复前 11 个位 5 个不同值，
   > 修复后 11 个位 11 个不同值。这类问题靠眼睛只能感觉"有点怪"，
   > 靠数字才能当场断言。

#### ⚠️⚠️ 这里踩过的最大一个坑：**判据选错了对象**

铺垫段的起始位置，原判据是「窗口里**装进了**多少种动作」——
理由听起来很自然：「铺垫段不该无聊」。

但**铺垫段是连续长镜**：窗口里的事件是被连续播一遍的，**根本不作为锚点使用**；
而窗口每往后挪一步，就多吃掉一点本来能给快剪段当锚点的素材。

> 这个判据在**优化一个不参与产出的量，代价却是产出本身**。

实测（25s 素材 / 7 个快剪实拍位）：

| 铺垫段起点 | 能给快剪段留下的动作种类 |
|---|---|
| 0.000 | **7 种** |
| 0.833 | 6 种 ← 旧判据选的正是这个 |
| 1.667 | 5 种 |
| 4.167 | 4 种 |

起点 0.833 刚好吞掉 **8.865s 的「抬头」**—— 那正是第 7 种动作类型。
症状看起来是「素材动作密度不够、上限就是 6 种」，
**实际是被自己的判据吃掉了**，而报告里还写着「精确 DP 算出的上限」，
看起来很客观。

**修法**：改成按「它给下游**留下**什么」择优，该判据本身降为**末位**：

```
(能填满几镜, 能覆盖几种动作, 锚点总强度, 铺垫段自身丰富度, 越靠前越好)   字典序
```

> **配套铁律**：搜索用的选择函数与正式渲染**必须是同一个**。
> 否则报告里写的「最多能凑 N 种」与真正选出来的不是一回事 —— 那种数字比不报还糟。
> 这就是 `select_anchors()` 被单独抽出来的原因。

#### ⚠️ 顺带修掉：搜索范围上限来自一个**几十毫秒的空隙**

旧上限取自 `first_run_end`（「从 0 起第一个连续的动作覆盖区」），本意是
「铺垫段要落在一段有内容的素材里」。但那条边界是上游分区拼出来的，**极脆弱**：

```
4.82 → 4.88  空隙 0.067s   ← 就是它把上限从 14.425 砍到 4.818
```

于是「把铺垫段挪到后面、把开头的表情让给快剪段」这个选项，**优化器根本没被给到**。

**修法**：搜整条素材；「铺垫段不能冷清」改用一条**非参数**门槛 ——

> 铺垫段的丰富度 ≥ **所有候选位置丰富度的中位数**，
> 即「至少得像这份素材里一个**典型**的 8 秒」。

用**中位数**而非常数：门槛由素材自己决定，不掺外部调参，
换个素材也不会因为门槛过紧而卡死（全部不达标时退回全体择优）。
它只是**护栏**、不参与择优 —— 实测本片门槛不生效（候选 4.029 > 中位 3.679）。

#### ⚠️ "凑不满"的第一嫌疑是**素材总时长不够**，不是算法（2026-09-24）

卡点版对素材的总需求量是可以直接算出来的，**先算再怀疑算法**：

```
需求 = 正常段 8.086s + 快剪实拍位 11 × 0.633s（源消耗） = 15.049s
```

| 素材 | 时长 | 余量 | 结果 |
|---|---|---|---|
| `录制_raw_0924_082604.mp4` | 15.03s | **0.1%（等于零）** | 11 个位只有 5 个命中动作峰值 |
| 网页默认录制 | 25s | ≈10s | 空档从 6.8s 变 ≈17s，峰值挑得开 |

素材刚好等于需求时，**任何**取段算法都不可能挑出 11 个互不重叠、还各自压在
峰值上的窗口 —— 那时"凑不满"是**素材的物理上限**，报告里那句
"这是当前配置下的上限"说的就是这件事。**对策是录长一点，不是改算法。**

> ⚠ 网页录制的上限是 `REC_MAX_FRAMES = 800` 帧（≈28.9fps 下 **27.7s**）——
> 触顶会提前收尾。要 25s 没问题，想录更长得先调这个常量。

#### 效果：7 种 / 7 镜，且锚点强度翻倍

| | 改前 | 改后 |
|---|---|---|
| 铺垫段源区间 | [0.000, 8.045] | **[15.233, 23.279]** |
| 快剪 7 镜动作 | 抬头 / 眨眼 / 转头 / 凑近 / 后退 / 张嘴 / 摸头 | **微笑 / 凑近 / 眨眼 / 举手 / 抬头 / 转头 / 后退** |
| 动作类型 | 6 种 + 复用「转头」 | **7 种 / 7 镜，零复用** |
| 锚点总强度 | 2.361 | **4.906** |
| 实拍占用 | 16.09s / 25.01s（0 重叠、0 越界） | 同 |

`微笑 +0.897`、`举手 +1.604` 这类**表情/大幅度动作**进来之后，
「素材动作密度不够」的问题自然消失了 —— 它们本来就在素材里，
只是之前被铺垫段吃掉了。

> ⚠ 这里有个容易说过头的地方：**「凑不满」是「当前配置下的上限」，不是素材的物理极限**。
> 所以在真的发生复用时，程序会自动跑一次**精确 DP**（不是贪心估计）算出
> 「空档内最多放得下几种」，把约束条件一并打出来：
>
> ```
> 约束 = 镜头不重叠 + 峰值固定落在镜内 35% + 结尾预留 1.79s
> 可放锚点的空档 [8.05, 23.22] 内最多放得下 6 种不同动作
> ```
>
> DP 的状态是「动作集合的位掩码」（≤14 种 → 16384），
> 候选窗口按结束时间排序，选/不选两个转移 —— 窗口几十个，秒级出结果。
> **位掩码必须是 `1 << 类型序号`，不能拿序号当掩码**（`抬头(8) | 眨眼(11) == 11 == 眨眼`，
> 组合会被集合去重吃掉；症状是小用例正常、窗口一多就崩）。

#### 指定动作：`--action-plan`（2026-10-09）

上面的挑选是**自动**的：算法决定哪个动作落在哪个位置。`--action-plan` 让用户直接指定。

```bash
python edit_slop.py --clips clips/reel_map.json --material 素材.mp4 \
       --action-plan "3=举手,7=转头"
```

**编号是「槽位」** —— 快剪段第几个**实拍位**，从 1 开始。微波炉对（正放+倒放）
在画面上是**一个**单元，所以算**一个**槽位（不是两拍）。不知道哪个槽位是什么，
跑一次 `--dry-run` 会打出对照表：

```
  实拍位（槽位）一览 —— --action-plan 用这个编号，共 8 个：
      槽位    首分镜  效果              入点  动作       指定
       1     20  mirror       0.139  嘟嘴       —
       2     22  boom         1.039  转头       —
       3     25  boom         3.163  挑眉       —
       4     28  zoom        10.290  举手       指定 举手 ✓
```

| 规则 | 说明 |
|---|---|
| 未指定的槽位 | 照旧自动挑（两轮：每类一次 → 放开重复） |
| 指定的动作 | **允许重复**（写两次「举手」就出两次），不受"每类只用一次"限制 |
| 指定先满足 | 按槽位序钉住指定动作，其余槽位再自动补 |
| 非指定槽位 | 事后按时间升序重排 —— 保住"越靠前的镜取越靠前的源"这个历史性质 |

**⚠ 三个必须说清楚的点**

1. **指定必须加在共用的 `select_anchors()` 内部，不能在外层过滤。**
   搜索铺垫段位置与正式渲染必须看到同一套约束（见上面的「配套铁律」）。
   顺带的好处：指定动作会**反过来影响铺垫段位置的搜索** —— 判据首位加上
   「指定落实了几个」，优化器于是会主动把铺垫段挪开、把指定动作的峰值让出来。
2. **护栏与指定冲突时，指定优先。**
   踩过：指定「举手」时，该动作的峰值（10.51 / 13.00s）只有在铺垫段起点
   ≥ 10.93s 时才不被吃掉，而那些位置的丰富度**全部**低于中位数护栏
   （2.076 vs 2.196，只低 5%），于是护栏把唯一可行的区间整段砍掉、
   指定**永远落不了地** —— 用户会以为是自己把动作名写错了。
   现在：护栏只用于**同等落实数之间**的择优；若落实最多的那一档整体被挡住，
   就放开护栏并在报告里明说。无 `--action-plan` 时这条逻辑完全不生效。
3. **不落实就报出来，不静默降级。** 三处都报：逐镜 `note`、
   槽位表里的 `✗ 未落实`、汇总行 `指定落实 1/2 ⚠`；
   再由 `verify_contentaware.py` 的 `[3]` 做机器验收。
   格式错 / 动作名不存在 / 忘了带 `--clips` —— **一律当场报错退出（码 1）**。

实测（25s 素材，8 个槽位）：

| 指定 | 结果 |
|---|---|
| `4=举手,6=后退` | 落实 2/2 ✓；铺垫段让位后**动作种类反而从 5 种升到 6 种** |
| `1=挑眉,2=挑眉` | 全片只有 1 个「挑眉」峰值 → 落实 1/2，槽位 2 告警并退回自动 |
| `1=双手举` | 本素材没有该动作 → 报错退出，并列出可用的 7 种 |
| `2=举手,99=后退` | 槽位 99 越界 → 告警并忽略；分母只算有效的 1 个 |

> ⚠ **只管实拍侧。** 交错素材（贝特曼那条）仍是**从头顺序消耗**的游标，
> 不参与内容感知 —— 要对素材侧做动作挑选，得先对参考片跑一遍
> `action_detect.py`，那是另一件事。

#### 验收（verify_contentaware.py）—— 必须回到画面上量

剪辑器打印的"命中 7/7、落位偏差 0ms"**是方案自己的数字**。
方案说入点是 13.878s，不代表渲染真的取了那一帧。所以另写一个验收，
对照 **方案 vs 真实渲染出的画面**：

```bash
python verify_contentaware.py 成片.mp4 --plan 成片.plan.json
```

**[1] 内容匹配（对照式）** —— 取成片镜中帧与源片几个候选时刻做归一化互相关：

| 候选 | 含义 |
|---|---|
| 内容感知入点 | 应该最高 |
| **旧「顺序游标」入点** | 对照组：改造前会用的位置 |
| 入点 ±1.2s | 对照组：邻域错位 |

用对照组而不是绝对阈值 —— 画面经了模糊底/叠化/调色/颗粒/色差，
绝对相关系数本来就不会是 1，只有"跟别的候选比更高"才说明问题。

实测（竖屏/方形均同）：**胜出 7/7**，内容感知 0.967~0.992，
旧顺序 **0.461~0.846**，±1.2s 错位 0.581~0.935。

另有两项，按方案内容决定跑不跑：

| 项 | 什么时候跑 | 判据 |
|---|---|---|
| [2] 黑白镜 | 只有复刻版有逐镜黑白（卡点版 `--bw` 是全局降饱和，本项跳过） | 黑白组的色度比必须**全部低于**彩色组的最小值 —— 判定线取"彩色组最小值"，不含任何人为阈值 |
| **[3] 指定动作** | 方案里有 `--action-plan` 才跑 | 每个指定槽位的分镜 `action` 必须**等于**指定值；另核对方案自记的 `action_plan_ok` 与实际核对数是否一致 |

[3] 存在的理由：指定动作在可行域内找不到时会**退回自动**（不是报错中断）。
只靠肉眼看成片，「指定了却没落实」极易漏掉 —— 正是本项目反复强调的那类静默降级。

### 相位必须在目标段落内拟合

同一个手写实现，用**全局相位**在 Drop 段命中率是 **0%**，
换成**在 Drop 段内重新拟合的相位**就是 71.4%。

原因：整首歌的相位会被前奏/主歌带偏，而剪辑只用到 Drop 段。
用包含不同段落的数据拟合单一相位，会被结构差异污染。

> 这解释了很容易误判的现象：**"全局看起来还行，切出来却卡不准"**。

| 方案 | Drop 段命中率 | 中位偏差 |
|---|---|---|
| 手写（全局相位） | 0.0% | 71.7ms |
| 手写（分段精修相位） | 71.4% | 37.0ms |
| **librosa** | 71.4% | **23.2ms** |

### 相位搜索的目标函数不能只看命中率

命中率会**饱和**（Drop 段最多压住 71.4%），所以两个不同相位给出**相同命中率**：

| 相位 | 命中率 | 中位偏差 |
|---|---|---|
| 0.0677（旧） | 71.4% | 37.0ms |
| **0.1033（现用）** | 71.4% | **4.4ms** |

目标函数必须**把精度（中位偏差）纳入**。现用 `PHASE = 0.103266`
（`refine_phase.py` 细扫 20000 个候选选出）。

## 为什么录制阶段不收麦克风

成片的音轨固定用 BGM，卡点也建立在该 BGM 上，所以录制**不需要收声**。
这样做有三个实际收益：

1. **不再受麦克风故障影响** —— 本机麦克风此前实测几乎无信号（最大 RMS
   只有 3/8/12/103），收声等于白收
2. **素材与配乐解耦** —— 换一首 BGM 不用重录素材（实测：同一素材
   128BPM 出 3.74s，100BPM 出 4.80s）
3. **录制更稳** —— 少一个音频线程和每帧的队列抽干

> 早期版本实现过麦克风采集 + 按 RMS 分位判定"说话帧"。
> 若将来要做**人声口播 + BGM 混音**，那段逻辑的教训记在
> `sigma_realtime.py` 的注释里，最关键的一条是：
> **判定阈值必须用分位数，不能用中位数。**
> RMS 分布是双峰的（静音 ~30 / 说话 ~6000，中间几乎无样本），
> 中位数会落进两峰之间的空档（实测 2808），乘 2.2 得 6177 ——
> **比说话电平本身还高**，导致 47/50 被误判为静音。

## 卡点是怎么算准的

核心矛盾：**变速会改变画面时长，而 BGM 是固定的。**
所以不能"先变速再看卡点准不准"，必须反过来 —— 以 BGM 的节拍时间轴为基准，
去决定画面在第几秒该快、第几秒该慢。

```
BGM 分析   解码 → 能量包络(20ms窗/5ms跳) → 起点正差分 → 估BPM → 相位对齐
    ↓     产出 beats[] / downbeats[] / offset
卡点规划   目标时长 = N 个强拍（4 强拍 @128BPM = 7.5s）
    ↓      让变速把素材压到恰好这个时长；慢放段**中点**压在强拍上
渲染       素材 + BGM → 变速滤镜 + atrim 截取 + 淡出 → 竖屏成片
```

两个关键设计：

**1. 锚点对齐的是慢放段的"中点"而不是"起点"。**
慢放的视觉冲击在段中部最强，若让起点对齐强拍，"最慢那一帧"会落在强拍
之后半个段长。校验时必须比对 `anchor + slow_window/2`。

**2. 时长由"输出侧"累加，不由输入侧推导。**
不变式是 `Σ(加速段输出) + Σ(慢放段输出) == target_duration`。
早期版本按输入侧累加，得到 `total_out=24.56s` vs `target=7.5s`（偏差 227%）。
素材长度则是反推量：`素材 = 输出 × 速度`。

## 技术实现

1. **采集** — OpenCV `VideoCapture`，优先 DSHOW 后端
2. **检测** — MediaPipe FaceLandmarker（478 人脸点）+ PoseLandmarker（33 姿态点）
3. **合成** — 按模式渲染关键点与视觉模板
4. **导出** — ffmpeg 转竖屏**无声**素材
5. **配乐卡点** — `beat_analyze.py` → `beat_sync.py` → `bgm_pipeline.py`

## 性能

实测 **13-15 fps**（1280x720）。三处关键优化：

1. **检测分辨率降采样**：检测用 640 宽小图，渲染用原图
   （MediaPipe 返回归一化坐标，缩放不影响渲染正确性）
2. **姿态检测降频**（`POSE_EVERY=2`）：姿态比人脸贵约 50%，隔帧复用
3. **暗角遮罩预计算**：逐像素 float32 运算 75ms/帧 → 缓存 uint8 遮罩 +
   `cv2.multiply` 降到 3.2ms（23 倍）

优化前后：**4.4 fps → 15.2 fps（3.5 倍）**。

### 验证方法本身也有坑（值得记下）

- **验证闪白不能用"比邻帧亮"**：快剪段每拍硬切，两个源亮度差极大，

## 三个 Windows 特有的坑（都已实测踩过）

**1. 删临时文件必须重试。**

`cv2.VideoWriter` 写完 `.release()` 后、以及 ffmpeg 刚读完输入文件时，
系统句柄未必立刻释放，`os.remove` 会**间歇性**抛 PermissionError。
实测连跑 3 次有 **2 次**留下 `_raw_*.mp4`。

这个失败极难发现：只打一行日志，测试输出一被重定向就完全看不见。
所以用 `_robust_remove()` 递增退避重试（修复后连跑 8 次 0 残留），
并在 `test_audio.py` 里补了 [1b] 回归用例。

**2. 本机没有 `ffprobe`，且 `ffmpeg -i` 的退出码总是 1。**

读元数据只能解析 `ffmpeg -i` 的 stderr，而它**总是返回 1**（因为没给输出文件）。
判定必须看"有没有解析到内容"，**绝不能看 returncode**。

**3. `.bat` 里不能写中文 —— 会把批处理指令劈碎。**（2026-09-24 实测）

`启动网页.bat` 第一版用了 `chcp 65001` + 中文 `echo`，结果**服务根本没起来**：

```
'on.exe"' is not recognized as an internal or external command
'程占用' 不是内部或外部命令
'ord_auto.py' 不是内部或外部命令
```

`set PY="C:\...\python.exe"` 这一行被**从中间劈开**（只剩 `on.exe"`），
`record_auto.py` 变成 `ord_auto.py` —— cmd 是按字节偏移增量读取批处理文件的，
**中途 `chcp` 切码页会让后续行的边界整体错位**，行被切成碎片当成命令执行。
症状极具误导性：看起来像 python 路径写错了，其实是文件被读花了。

三组对照实验（同一份内容，只改一处）：

| 换行 | echo 内容 | 服务起来 | 被劈碎的指令 |
|---|---|---|---|
| LF | **ASCII** | ✓ | 0 条 |
| CRLF | **ASCII** | ✓ | 0 条 |
| CRLF | 中文仅在 `rem` 注释里 | ✓ | 0 条 |
| LF | **中文 echo** | ✗ | **4 条** |

→ 与换行符无关，**只与 bat 里有没有非 ASCII 字节有关**。

**做法：`.bat` 保持 100% ASCII（连 `rem` 注释也不要写中文），中文说明全部交给
Python 打印** —— Python 走 `WriteConsoleW`，控制台是哪个码页都能正常显示中文。
`启动网页.bat` 因此只有 1153 字节、非 ASCII 字节数 **0**，启动横幅里的中文
是 `webapp.py` 打的。

> 项目里另外三个 bat（`启动.bat` / `套模板.bat` / `卡点成片.bat`）都是
> UTF-8 + `chcp 65001` + 中文 echo，属**同一类隐患**。它们目前能用，是因为
> 错位恰好落在 `echo` 文本里（echo 打印什么都是打印）；一旦关键命令行落在
> 错位区间就会以同样的方式失效。要动它们之前建议先按这个模式改干净。

## 已知限制

- 单人检测（`num_faces=1` / `num_poses=1`）
- 录制时帧数据全部留在内存（15fps 720p 约 33MB/秒），长时间录制占内存

## ⚠️ 一条被反复踩中的归因陷阱（值得单独记）

**"只测一个工况就下通用结论"** —— 本项目里同类错误出现了四次：

| 曾经的错误结论 | 真相 |
|---|---|
| 「`setpts` 里的减号导致解析失败」 | 是裸的 `<` `>` 不被支持，与减号无关 |
| 「`crop` 表达式不能加引号」 | 必须加引号（含逗号时） |
| 「`gblur` 的 sigma 能用 t 表达式」 | 不能，必须用 `tmix` 走时间维度 |
| 「trim 的 1 帧余量完全没必要」 | **只在 `slices=1` 下没必要**；`slices=2` 时缺它每镜少 1 帧 |

最后一条是最近一次（`probe_pad.py` 可复跑，只改 padding 一个变量）：

| slices | 每镜时长 | padding=0 | padding=1 |
|---|---|---|---|
| 1 | 0.469s | 562 帧 ✓ | 562 帧 ✓ |
| **2** | **0.234s** | **518 帧 ✗（44 镜各少 1 帧，成片短 1.48s）** | 562 帧 ✓ |

原因：`trim=duration` 取到的**最后一帧时间戳是 k/fps**，实际覆盖的时间跨度
比 duration 少最多 1 帧。长切片时这点差距被帧吸附吸收；短切片时吸收不掉、
逐镜累积。

> **通用教训**：下"通用"结论前，必须让被测变量**覆盖到极端工况**。
> 只在默认参数下测出的行为，不能外推到参数空间的其他角落。
> 这与"两个变量同时改一定会归因错"是同一类问题的两面。

## 本机 ffmpeg 表达式规则（实测，含一处已更正）

三个滤镜的表达式规则**各不相同，不能互相套用**。
`probe_ffmpeg.py` 把这些做成了可复跑的矩阵测试：

| 滤镜 | 逗号 | 时间变量 | 裸 `<` `>` |
|---|---|---|---|
| `setpts` | 必须转义 `\,` | 大写 `T` | **不能用** |
| `eq` | 引号内不用转义 | **小写 `t`**（大写 `T` 会挂） | 可用 |
| `crop` | **必须加引号** | `t` / `n` | 可用 |

> ### ⚠️ 一处已更正的旧结论
>
> 之前记的是「`setpts` 里的裸减号会导致 `Missing ')'`，要改成 `+-`」。
> **这是错的。** 实测真相是**裸的 `<` `>` 比较运算符不被支持**：
>
> ```
> setpts=(T<0.5)*(PTS-0.5)    →  Missing ')'   ✗
> setpts=(T<0.5)*(PTS+-0.5)   →  Missing ')'   ✗  ← 旧文档称"可用"，实测挂
> setpts=(T<0.5)*(PTS+0.5)    →  Missing ')'   ✗  ← 无减号也挂！
> setpts=(T>0.5)*PTS          →  Missing ')'   ✗
> setpts=lt(T\,0.5)*PTS       →  正常           ✓
> ```
>
> **误判原因**：当时失败的例子 `(T<1.4)*(PTS-1.4)` **同时含 `<` 和 `-`**，
> 改掉减号时恰好也换成了函数形式，于是归因到了错的那个变量上。
>
> **教训**：验证"某字符是否是元凶"时，必须构造**只含该字符**的最小用例。
> 两个变量同时改，一定会归因错。
