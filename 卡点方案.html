01先回答你的三个问题

Q1：能写成脚本自动执行吗？需要剪辑软件 API 或 MCP 吗？

能，而且完全不需要剪辑软件 API 或 MCP。 整条流水线只用 ffmpeg 一条命令行完成 —— 硬切、变速、闪白、抖动、RGB 分离、VHS 颗粒、竖屏、配乐、淡出， 全部是 ffmpeg 滤镜。

为什么不需要剪映/PR 的 API：那些软件的价值在手工拖时间轴， 而我们的切点是算出来的（对齐 128BPM 拍网格），不是拖出来的。 算好的切点直接生成 filter_complex，比调 API 更直接、更可复现。

什么时候才需要 API/MCP：需要人工微调、需要模板库（剪映的"一键成片"）、 或者要输出到特定平台工程文件时才值得。纯"算法卡点"用不上。

Q2：GitHub 上有没有好的开源音频分析项目？

有，而且我真的装上对比过了（不是只列名字）：

04手写 vs librosa：实测对比

你要求"别造轮子"，所以我把 librosa 装上做了同口径对比。 判据不是"谁的数字好看"，而是谁的网格更能压住底鼓 —— 这是剪辑真正关心的量。

方案Drop 段命中率中位偏差
手写（用全局相位）0.0%71.7ms
手写（分段精修相位）71.4%37.0ms
librosa71.4%23.2ms

最重要的发现：问题不在 BPM，在「相位必须在目标段落内拟合」

同一套手写代码，用全局相位在 Drop 段命中率是 0%， 换成在 Drop 段内重新拟合的相位就是 71.4%。

原因：整首歌的相位会被前奏/主歌带偏，而剪辑只用到 Drop 段。 用包含不同段落的数据去拟合单一相位，会被结构差异污染。

这解释了一个很容易误判的现象："全局看起来还行，切出来却卡不准"。

方法论 BUG相位搜索的目标函数选错了

原来我用命中率当唯一判据，搜出相位 0.0677（命中率 71.4%）。 但命中率会饱和 —— Drop 段最多只能压住 71.4% 的底鼓 （有些击打本就不在主拍上），所以：

相位命中率中位偏差
0.0677（旧）71.4%37.0ms
0.1033（新）71.4%4.4ms

命中率完全相同，精度差 8 倍。只看命中率永远挑不到好的那个。

修正：目标函数改为「先比命中率、同分时比中位偏差」，细扫 20000 个候选。 现用 PHASE = 0.103266。

05开发中抓到的三个隐蔽 Bug

这三个都属于「代码看起来对、数学也对，但成片是坏的」。 全部靠量化指标抓出来，肉眼看不出来。

BUG 1多输入滤镜的输出被多处消费 → concat 尺寸不匹配

✗ ...overlay=...[n];[n]trim=...[a];[n]trim=...[b];[a][b]concat...
   → Input link in0:v0 (1280x720) 不匹配 (1080x1920)
✓ ...overlay=...[n];[n]split=2[n0][n1];
                  [n0]trim=...[a];[n1]trim=...[b];[a][b]concat...

overlay 是多输入滤镜，输出尺寸靠主输入推导（不是固定值）。 它的输出被多个下游消费时，ffmpeg 自动插入的 split 会让尺寸推导链断掉， 下游拿到的是源尺寸。

最阴的地方：这个坑只在"源尺寸 ≠ 目标尺寸"时暴露。 用小尺寸素材测试能通过，换真实大尺寸突然失败。

已排除的无效尝试：在 overlay 后补显式 scale、补 format=yuv420p —— 都没用，只有显式 split 有效。

BUG 2拍周期不是整数帧，误差逐段累积

128 BPM 的拍周期 0.46875s，在 30fps 下 = 14.0625 帧（不是整数）。 40 个片段首尾相接，每段四舍五入，误差累加 0.15s。

后果：后半段画面偏离 BGM，且按时间表达式触发的闪白会整帧错过。

解法：每段输出起点吸附到理想网格的最近帧， 而不是"上一段结束的最近帧" —— 前者每段重新对齐，误差永远 ≤ 半帧； 后者会累积。

BUG 3trim 少取 1 帧，40 段丢 16 帧

trim=duration 按时间截断，若时长不是帧长整数倍， 实际帧数会比需要少 1 帧，随后的 fps 归一化就少产 1 帧。 成片从 18.75s 缩到 18.20s。

解法：trim 时长多给 1 帧余量，fps 会正常丢掉多余帧。 修好后成片精确 18.75s。

验证方法本身也踩了两个坑（值得记下）

1. 验证闪白不能用"比邻帧亮"。 快剪段每拍硬切，两个源亮度差极大，每次硬切都产生亮度跳变 —— 结果 22 次切点全被误判成闪光（检出 30 个假事件）。 必须用绝对阈值（接近纯白）。

2. 验证硬切不能用 99 分位当阈值。 那等于只取最大的 1%，最多检出 5 个，会把"检出 3/23"误读成"切点没压上" —— 其实是检测器自己把范围限死了。

共同点：测量对象/阈值选错，会得出完全相反的结论。

07顺带更正了一处旧结论

已证伪「setpts 里的减号会导致解析失败」

这条结论之前写进了 skill，这次用矩阵实测推翻了：

setpts=(T<0.5)*(PTS-0.5)    →  Missing ')'   ✗
setpts=(T<0.5)*(PTS+-0.5)   →  Missing ')'   ✗  ← 旧文档称"可用"
setpts=(T<0.5)*(PTS+0.5)    →  Missing ')'   ✗  ← 无减号也挂！
setpts=(T>0.5)*PTS          →  Missing ')'   ✗
setpts=lt(T\,0.5)*PTS       →  正常           ✓

真正的规则：这个 ffmpeg 构建不支持裸的 < > 比较运算符，必须改用 lt() / gt() / gte() 函数。

为什么会被误判成减号：当时失败的例子 (T<1.4)*(PTS-1.4) 同时含 < 和 -； 改掉减号时恰好也换成了函数形式，于是归因到了错的那个变量上。

教训：验证"某字符是否是元凶"时，必须构造只含该字符的最小用例。 两个变量同时改，一定会归因错。

生产代码没受影响（全部用的是 lt()/gte()，grep 确认 30 处 gte + 17 处 lt）， 但 skill 里的文档和 _no_minus() 的说明已更正。
