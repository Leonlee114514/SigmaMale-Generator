一个关键认识：BGM 固定 → 只需分析一次

这跟"用麦克风实时判定节拍"是完全不同的两件事。BGM 固定带来三个好处：

  • 只分析一次，结果缓存成 json，导出速度不受影响
  • 可人工校正——分析结果是可读的 json，觉得 BPM 不对能直接改
  • 可复现——每次渲染的卡点都一致，不像实时判定会抖动

03关键设计决策

① 锚点对齐慢放段的「中点」

慢放的视觉冲击在段中部最强。如果让起点对齐强拍，"最慢的那一帧"会落在 强拍之后半个段长。

所以锚点 = 慢放段起点，而真正压住强拍的是 anchor + slow_window/2。

这个语义必须写清楚，否则校验时拿 anchor 直接比对强拍， 会得到"全部偏差 540ms"的假失败。

② 时长在「输出侧」累加

不变式：Σ加速段输出 + Σ慢放段输出 == 目标时长。

素材长度是反推量：素材 = 输出 × 速度。素材不够就慢放补， 多了就加速压——这正是"视频适配音频"的含义。

早期版本按输入侧累加，得到 total_out=24.56s vs 目标 7.5s（偏 227%）。

③ offset 必须参与运算

BGM 的第 0 个强拍不一定落在 0.0s（前奏/淡入会让首拍后移）。

若忽略 offset，所有慢放段整体偏移 offset 秒，而偏差量恰好等于 offset （1:1）——offset=0 时"看起来完全正确"，offset=0.456 时错 456ms。

④ 素材 / 配乐解耦

录制只出无声素材，配乐在后期混入。

实测收益：同一段素材，128BPM 出 3.74s，100BPM 出 4.80s， 不用重录。

04开发中抓到的三个真实 Bug

这三个都值得单独说，因为它们的共同特征是： 纯数学单元测试全绿，但成片是坏的。

BUG 1分段表达式漏了乘号 → ffmpeg 报 Missing ')'

✗ ...(T<2.26)(T>=2.26)*(T<2.64)...     // 相邻括号并列
✓ ...(T<2.26)*(T>=2.26)*(T<2.64)...    // 区间之间也要 * 连

每个区间内部用 * 连是对的，但区间与区间之间也必须用 *。用 "".join() 拼条件时极易漏掉分隔符。

危险点：拼出来的字符串在 Python 里"看起来完全正常"， 只有真交给 ffmpeg 才炸。

BUG 2双重转义 → No such filter: '2.2645)\'

我自己写了 \,，又交给统一的转义函数转了一次，变成 \\,。

判据：报错里出现带反斜杠的片段，就是转义了两次， 而不是"逗号没转义"。

教训：转义权只能有一处，传入裸表达式。

BUG 3fit_to_beats 忽略 offset

症状极具迷惑性：偏差恰好等于 offset，而 offset=0.000 的用例是"通过"的。 只测 offset=0 就会漏掉。

顺带做的重构（比修 Bug 更有价值）

把"掩码相加法"整体换成"从后往前的嵌套 if"。掩码法里第 i 段要写成 "落在第 0..i 段全都满足"，长度天然是 O(N²)；嵌套 if 是 O(N)。

段数掩码相加嵌套 if
8 段1.06 KB0.38 KB
32 段13.8 KB1.58 KB
128 段（继续平方增长）6.42 KB

附带好处：语义直白、能手改。约束是嵌套深度 ≤ ffmpeg 的 max_nesting（默认 40），32 层安全。

为什么必须有端到端测试

算法测试全绿不代表成片正确。BUG 1 和 BUG 2 都是 "表达式数学正确、但 ffmpeg 直接拒绝执行"。

端到端测试判定的是硬指标：退出码、文件大小（>1KB 挡住 0 字节静默失败）、 成片时长、音轨有无。不看观感——观感无法评审，也无法回归。

07怎么用

# 1) 录制素材（对着摄像头玩，按 R 开始/停止，再按 R 停止并导出）
python sigma_realtime.py

# 2) 把 BGM 放进 bgm\ 目录，然后分析一次
python bgm_pipeline.py --analyze-only

# 3) 卡点成片
python bgm_pipeline.py --downbeats 4 --grade sigma

也可以直接双击 启动.bat / 卡点成片.bat / 套模板.bat。

两个脚本的分工

脚本管什么
slop_apply.py只管画面（变速/调色/抖动/RGB/构图），不碰音频
bgm_pipeline.py只管卡点 + 配乐

分成两步是因为画面滤镜会改变时长。一次性写完会让算锚点依赖的 "输出时间轴"失效，卡点整体漂移——而漂移量恰好等于时长变化，肉眼极难发现。
